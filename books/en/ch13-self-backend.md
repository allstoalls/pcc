# Chapter 13: The Self Backend — Native Emission without LLVM

In Chapter 12 LLVM was pcc's emission engine; in this chapter it steps back to the role of reference. The self backend under [pcc/backend/](../../pcc/backend) is a native assembly emitter that calls no LLVM library: it reads LLVM IR text and writes AArch64 Darwin assembly directly (plus an x86_64 Linux subset). Its reason for existing is obligation 4 of the seven — the self backend must become a first-class execution root, with LLVM as oracle, not owner. This chapter establishes three things: why the bootstrap fixed point forces this backend into existence; how an "asm-first" emitter that deliberately performs no global register allocation is layered (a target-independent parse/layout/stack-slot core, target-specific emitter families, a text peephole layer); and two boundary obligations — no silent fallback to LLVM after `--backend=self`, and `_link_with_self_backend` must not pull `pcc.backend.*` back into the stage1 closure. Where the backend's input comes from (Python-frontend lowering, Chapter 6) and the bootstrap gate itself (Chapter 15) are out of scope here.

## Chapter Overview: Read Boundaries before Instructions

Do not begin with assembly details. First fix the self backend's boundary in your head: it reads LLVM IR text, owns instruction selection and ABI emission, still delegates assembling and linking to system tools, may reject unsupported shapes, and may not silently route back to LLVM after `--backend=self`.

- The self backend exists for bootstrap ownership, not to replace all of LLVM's optimization capability immediately.
- "Asm-first" means emitting correct assembly text first, before full register allocation or object-file writing.
- Each `BackendUnavailable` is an honesty boundary: no guessing, no hidden fallback, no pretending a shape is supported.

## 13.1 The Problem and the Design Space: Why Write a Backend at All

Start with the obvious objection: LLVM works, so why build another emitter? The answer is not performance; it is the last link in the chain of ownership. pcc's thesis (Chapter 1) requires compiled artifacts that are native, auditable, self-hostable, and no-libpython; the bootstrap chain pcc1→pcc2→pcc3 requires that pcc1 — a native binary that links no libpython — can perform native emission on its own. If emission must pass through the LLVM library, then every compiler stage either links a vast external C++ codebase or loads it at runtime, and the fixed point forever embeds a black box that pcc neither owns nor can audit line by line. [goal-prompt.md](../../docs/goal/goal-prompt.md) §10 closes that road explicitly: "LLVM may be used as an oracle and fallback baseline, but it must not become the final dependency."

But "not depending on LLVM" has to be unpacked under claim hygiene, because LLVM appears here in three distinct roles, and each role has a different fate:

1. **LLVM as a library**: absent from the strict bootstrap chain. The compiled pcc1 generates IR text with [pcc/ir/ir.py](../../pcc/ir/ir.py) — a pure-Python "text-first IR builder" (its file header says so itself: incremental construction of IR text, no object graph) — the self backend parses that text and emits assembly, and the system `cc` assembles and links. No LLVM library call exists anywhere on the chain.
2. **LLVM as an IR dialect**: kept. The self backend's input remains LLVM IR text format. This is a deliberate bridging decision: the same IR can be fed either to LLVM or to the self backend, which makes differential comparison practical — [tests/c/test_llvm_self_vector_parity.py](../../tests/c/test_llvm_self_vector_parity.py) compiles and runs the same IR down both roads and compares exit codes and output, while [tests/c/test_c_testsuite_self.py](../../tests/c/test_c_testsuite_self.py) and [tests/c/test_gcc_torture_self.py](../../tests/c/test_gcc_torture_self.py) turn entire C test suites into oracle differential sources.
3. **LLVM as an optimizer**: off by default, present only by opt-in. On the C path, `_effective_self_backend_opt_level()` in [pcc/driver/cli_core.py](../../pcc/driver/cli_core.py) clamps the optimization level to 0 under `--backend=self` unless the environment variable `PCC_SELF_BACKEND_VECTORIZE` is explicitly set — and its doc comment states the reason plainly: the self backend does not yet lower LLVM vectorizer output (such as Lua's `<4 x ptr>` strcache broadcast). When the switch is on, the combination must be mode-labeled: LLVM optimized, self emitted. The two roles do not blur.

The roads not taken matter as much as the one chosen. (a) Build a full LLVM-style backend — instruction scheduling, graph-coloring register allocation — and the complexity of this one subsystem drowns every other goal in the repository. (b) An interpreter or a JIT — wrong artifact shape; the thesis demands a distributable native binary. The choice is (c) an **asm-first, bounded, faithful subset**: the module docstring of `self_backend_aarch64_darwin.py` enumerates the current support surface item by item (scalar integers, pointers, `alloca`/`load`/`store`, direct calls, integer arithmetic/comparison/branch/phi, scalar conversions) and states, in one sentence, the most important invariant this backend has — "Unsupported shapes still raise `BackendUnavailable` instead of guessing." That sentence is obligation 4 landing at instruction granularity: the backend would rather refuse to compile than emit code of doubtful semantics, and it never quietly switches roads.

The explicit-opt-in machinery lives in [pcc/backend/__init__.py](../../pcc/backend/__init__.py): `_BACKEND_TABLE` marks `self` as `supported: False`, with semantic version `self-aarch64-asm-v0` and the capability surface `emit-asm` / `emit-object` / `run-native-via-system-cc` / `aarch64-darwin-mvp`. `resolve_backend()` raises `BackendUnavailable` for unsupported backends by default; `backend_request_allows_unimplemented()` returns True only when the request **names** `self` explicitly (via the CLI or the `PCC_BACKEND` environment variable). In other words, choosing the experimental backend is itself the opt-in act — there is no path by which it is slid into by default — and `BackendConfig.cache_signature()` folds `kind:semver:support` into the cache identity, so artifacts from different backends cannot cross-contaminate at the cache layer either.

One last honesty boundary: **the self backend owns instruction selection and the ABI; it does not own the assembler or the linker.** The capability name `run-native-via-system-cc` says it outright — the `.s` text is handed to the system `cc -c` to become an object file, `cc` links, and on Darwin the result is additionally signed with `codesign`. The machine-code encoder and the Mach-O writer are delegated. "Asm-first" names exactly this boundary: it narrows the backend's correctness surface to "is the assembly text correct," leaving the byte-level details of object-file formats to platform tools. That is an MVP decision, not a statement of final form.

## 13.2 The Target-Independent Core: Text Parsing, Layout Algebra, and Stack-Slot Assignment

The layering principle for [pcc/backend/](../../pcc/backend) is written in the module docstring of `self_backend_parse.py`: handling of textual LLVM IR belongs to the target-independent layer, so that "parse results are reused by today's AArch64 Darwin and tomorrow's x86_64 Linux, rather than each target reimplementing IR text handling." `self_backend.py` itself has shrunk to a compatibility facade of a dozen lines (the old single-file backend used to live there).

**The parse layer** (`self_backend_parse.py`) is a family of per-line regular expressions: `_ALLOCA_RE`, `_STORE_RE`, `_BINOP_RE`, `_ICMP_RE`, `_CALL_RE`, `_GEP_RE`, `_PHI_RE`, and so on. `parse_self_backend_module()` produces a `ParsedModule` (triple, globals, functions); function bodies are cut into labeled basic blocks by `_parse_blocks()`, each line is normalized by `_parse_instruction()` into a `ParsedInstr(kind, data)` tuple, and terminators go through `_parse_terminator()` separately. Two details deserve to be named here, because the case studies in 13.7 return to both. First, `split_top_level()` is the only legitimate comma splitter — it tracks brace/bracket/angle/paren/quote depth, guaranteeing that an aggregate type like `{ i64, i64 }` is never torn apart at its field commas. Second, constant expressions (constant `getelementptr`, constant `inttoptr`, nested casts) are normalized by `decode_value_token()` into a small prefix language — `gepconst:base:offset`, `gep0:base`, `inttoptrconst:N` — so the emission layer never has to touch raw text again. Shapes that cannot be normalized raise `BackendUnavailable`, as always; `check_simple_symbol_name()` restricts the symbol surface to plain C identifiers.

**The data model** (`self_backend_ir.py`) is organized around `TypeDesc`: a frozen dataclass that carries both type description and layout algebra — `slot_size` (storage size in memory, with struct field alignment folded in), `value_slot_size` / `value_align` (the minimum-4-byte variants used for SSA value slots), `field_offset()`, and `aggregate_member_info()` (which walks an index chain to compute member type and byte offset, shared by `extractvalue`/`insertvalue`/GEP). `ParsedFunction` carries the complete ledger emission will need: `value_types`, `value_slots`, `alloca_slots`, `block_map`, `hidden_sret_slot`, `frame_size`.

**The analysis layer** (`self_backend_analysis.py`) does only lightweight dataflow: `instruction_defined_value()` / `instruction_used_values()` / `terminator_used_values()` enumerate definitions and uses per instruction kind; `collect_used_values()` yields the whole-function use set (results nobody uses get no slot and no emitted computation); `collect_block_local_last_uses()` finds values that are "used only within their defining block" together with their last-use point — and that is the entire basis for slot reuse in the next step. There are no global live ranges and no interference graph: this is a deliberate budget allocation — correctness first, with quality partially recovered later by the peephole layer.

**Stack-slot assignment** (`assign_stack_slots()` in `self_backend_stackprep.py`) carries the self backend's single most consequential design decision: **no register allocation — every used SSA value gets a stack slot in the frame.** Parameters are slotted first; if `aggregate_returned_indirect(ret_type)` is true, a `hidden_sret_slot` is reserved to hold the return-buffer pointer the caller passes in; then, block by block and instruction by instruction, every result value with a user is registered a slot. The only optimization is intra-block reuse: `alloc_value_slot()` first consults `block_local_last_uses`; a value that dies within its block returns its slot to the `free_slots` free list after its last use, and a later value can take it over if its size and alignment both fit. The total frame size is finally aligned to 16 bytes. What this "everything spills" model buys is complete locality of emission: code generation for each instruction is only "load from slot into fixed scratch registers → compute → store back to the destination slot." No cross-instruction register state is needed, and the output is deterministic — `tests/c/test_self_backend.py::test_self_backend_stack_slot_assignment_is_hash_seed_stable` pins slot assignment against hash-seed drift specifically, because any nondeterminism in emission order shatters the pcc2/pcc3 byte comparison directly (Chapter 15). A recent addition qualifies the "everything spills" model without replacing it: `self_backend_aarch64_darwin_regalloc.py` adds an *optional* conservative block-local register projection. The stack slot stays allocated for every value; on top of it, an integer/pointer SSA value whose entire lifetime is proven to stay inside one supported basic block can additionally live in a caller-saved register (x1–x8, unused by the call-free scalar lowering). Any block containing a call, phi, atomic, or otherwise unclassified instruction is rejected wholesale, so the slot model remains the correctness floor — this is still not the graph-coloring allocator rejected in 13.1.

**Module symbols** (`self_backend_module_symbols.py`) solve naming collisions in multi-module linking: `prepare_module_symbols()` sorts the module's public symbol set, takes its SHA-1, and uses `__pccmod_<hash-prefix>_` as the prefix for this module's `internal` symbols. Two modules with same-named `internal` functions no longer collide, and the prefix is content-derived rather than random — once again yielding to byte-level determinism.

## 13.3 The Dispatch Skeleton: A Target Registry and Two Dispatch Tables

Target selection used to be scattered conditionals; the module docstring of `self_backend_targets.py` declares the intent to stop that trend: "stop growing target dispatch as ad-hoc conditionals and instead expose a stable registry." The registry is a tuple of dataclasses:

```python
SELF_BACKEND_TARGETS: tuple[SelfBackendTargetSpec, ...] = (
    SelfBackendTargetSpec(
        identity="self-aarch64-darwin-v0",
        matches_triple=is_aarch64_darwin_triple,
        emit_asm=emit_aarch64_darwin_asm,
    ),
    SelfBackendTargetSpec(
        identity="self-x86_64-linux-v0",
        matches_triple=is_x86_64_linux_triple,
        emit_asm=emit_x86_64_linux_asm,
    ),
)
```

The entry point `emit_self_asm()` (`self_backend_dispatch.py`) parses the target triple out of the IR text — no triple means `BackendUnavailable` on the spot; the self backend does not guess targets — and `resolve_self_backend_target()` matches against the registry, refusing equally if nothing matches. After emission the result still passes through `run_self_target_pass_pipeline()` (end of 13.4).

The function-body emission skeleton is target-independent in the same way. `emit_function_blocks()` in `self_backend_emit.py` emits labels in block order, dispatches each instruction to emission callbacks, and finally emits the terminator. `self_backend_instruction_dispatch.py` offers each instruction first to `emit_memory` (alloca/load/store), then to `emit_compute` if unclaimed, and if neither claims it, raises a `BackendUnavailable` carrying the function name and block name. `self_backend_terminator_dispatch.py` takes one callback parameter for each of six terminator kinds: `ret_void` / `ret` / `br` / `br_cond` / `switch` / `unreachable`. Note the direction of the inversion of control: the dispatchers are shared, and each target backend injects its own emitters as callables — AArch64 and x86_64 consume the same skeleton, and a new target plugs in by the same shape.

## 13.4 The AArch64 Darwin Emitter Family

The emitter family is split by responsibility into a dozen-plus `self_backend_aarch64_darwin_*.py` files. The right reading order is: ABI and register conventions first, then per-instruction emission, then the module-level peepholes.

### Calling convention and ABI (`_abi.py`)

`reg_name()` chooses register names by type: `w` for integers of 32 bits or less, `x` for pointers and 64-bit integers, `s`/`d` for floats. `assign_abi_arg_regs()` keeps two cursors, GPR and FPR, eight registers each (x0–x7 / v0–v7); an argument that fails to get a register receives an empty tuple and goes to the stack. The rules for aggregates are deliberately narrow and explicit: `aggregate_reg_chunks()` accepts only aggregates whose members are all integers or pointers — ≤8 bytes goes in one register chunk, 8–16 bytes goes as an 8-byte chunk plus a tail chunk in two registers, and anything larger makes `aggregate_passed_indirect()` true: the caller spills the aggregate to memory and passes a pointer, and the callee receives that pointer in one GPR. Large aggregate returns follow the same rule: `aggregate_returned_indirect()` reuses the same predicate, the return-buffer pointer travels in x8 per AArch64 convention, and the prologue stores it into `hidden_sret_slot`. Stack arguments start at `[x29, #16]` (past the saved fp/lr pair), laid out by `stack_arg_offsets()` at 8-byte alignment each.

Darwin's variadics deviate from standard AAPCS64, and the backend follows the platform faithfully: **variadic arguments always go to the stack**, 8 bytes each (`variadic_stack_arg_storage_size()`); `emit_vararg_start()` sets the `va_list` to x29 plus the offset "just past the last fixed stack argument," and `emit_va_arg()` is the four-step "read pointer, load value, add 8 to pointer, write back" — supporting scalar results only, with out-of-bounds shapes refused as usual.

### Constants and scratch registers (`_regs.py`)

`emit_const_to_reg()` synthesizes arbitrary immediates with `movz`/`movk` in 16-bit chunks, skipping zero chunks; floating-point constants first try the `fmov` direct-immediate table (1.0, 2.0), otherwise borrow w12/x12 to move the integer bit pattern and `fmov` it across. The scratch-register discipline is fixed: x9/x10 conventionally hold operands, x11 the result, x12–x15 carry addresses; `pick_scratch_gpr()` chooses within x12–x15 while avoiding specified registers, and raises if it cannot. This fixed division of labor is not aesthetics: the peephole layer at the end of 13.4 performs liveness reasoning on raw text, and only under the convention "x9–x15 are the emitter's private preserve" is the text-level judgment "this mov can be deleted" a legitimate one.

### Prologue, returns, and terminators (`_prologue.py`, `_returns.py`, `_terminators.py`)

The prologue is textbook-shaped: `stp x29, x30, [sp, #-16]!`, `mov x29, sp`, adjust the stack by `frame_size`, then store each register argument into its slot, move stack arguments into slots via `emit_fixed_stack_arg_load()`, and copy indirect aggregate arguments wholesale through their pointers (`copy_address_to_slot()`). `emit_return_terminator()` splits two ways: an indirect aggregate return fetches the buffer address (delivered in x8) back out of `hidden_sret_slot` and block-copies the return value into it (with fast paths for zero-initialization and literals); a scalar return goes through `materialize_value()` into register 0 (x0/w0/s0/d0). Both ways share `emit_epilogue()`: restore the stack, `ldp x29, x30, [sp], #16`, `ret`. `unreachable` emits `brk #0`.

Phi deserves its own paragraph, because it is the single point of parallel semantics in this no-register-allocation model. Phis are separated from ordinary instructions already at parse time (`ParsedBlock.phis`), and at emission they are the responsibility of the **edge**: `emit_branch_terminator()` calls `emit_phi_assignments()` before jumping; a conditional branch has two edges with different targets, so `emit_cond_branch_terminator()` manufactures a `block_edge_label()` label block for the false edge, letting each edge perform its own phi copies before jumping to the real target; `switch` is emitted as a chain of "per-case compare + one phi-preparation block per edge" — no jump table, which is the honest shape of the current subset. Inside, `emit_phi_assignments()` handles the classic parallel-copy problem: if all phis are scalar and no source references any destination value, each is stored directly; otherwise a temporary area is opened below sp, all source values are written into the temporaries first, and only then moved into the destination slots — two phases that isolate reads from writes, so cyclic dependencies (the IR shape of `a, b = b, a`) cannot be destroyed by serialized overwriting.

### Per-instruction emission (`_memory.py`, `_compute.py`, `_ops.py`, `_slots.py`, `_mem.py`, `_addr.py`)

`emit_memory_instruction()` covers `alloca` (folded into the frame layout at compile time; zero instructions at run time) and `load`/`store`. Each has a fast path: when the pointer is a local `alloca` of this function and the types agree, the frame slot is accessed directly with `stur`/`ldur`, skipping address materialization; otherwise `materialize_pointer()` puts the address in x9 and the access goes through `store_value_to_address()`/`load_value_from_address()`. Large-aggregate accesses degrade to block copies (`copy_slot_to_slot()`, `copy_address_to_slot()`); `_mem.py` selects opcodes by size (`ldurb`/`ldurh`/`ldur`), and `aggregate_copy_chunks()` composes arbitrary sizes from 8/4/2/1-byte chunks in descending order.

`emit_compute_instruction()` is the big dispatch: binop, icmp/fcmp, casts, select, freeze, extractvalue/insertvalue, the vector subset (insertelement/extractelement/shufflevector and per-lane vector arithmetic), va_arg, GEP, call. Every scalar path follows the same rhythm — materialize operands into x9/x10, compute the result into x11, write back with `store_reg_to_slot()`. Hidden inside is a detail with the same lineage as the signedness theme of Chapter 4: narrow integers (i8/i16/i1) are **not kept in canonical sign-extended form in their slots**; they are re-canonicalized at sign-sensitive use points — `emit_compute_instruction()` calls `sign_extend_int_reg()` (`sxtb`/`sxth`; `and`+`neg` for i1) on both operands before `sdiv`/`srem`/`ashr` and before signed comparisons (`slt`/`sle`/`sgt`/`sge`). The lesson from the C codegen layer (signedness metadata getting lost) is structurally avoided here: sign semantics are carried by the IR instruction kind, and the backend pays the cost of re-extension at the use point in exchange for a single slot representation.

`materialize_value()` (`_materialize.py`) is the value-fetching confluence of the whole emitter family. In order, it recognizes: `null`/`poison`/`undef`/`zeroinitializer`; the constant prefixes normalized by the parse layer (`gepconst:`/`gep0:`/`inttoptrconst:`/`ptrtointconst:`/`negconst:`/`addconst:` plus the generic constant-expression prefix); `alloca` addresses (x29 minus offset); SSA values with existing slots; float and integer literals; aggregate literals that encode wholesale into one or two register chunks; and global symbol addresses. Global-address materialization (`materialize_global_address()` in `_addr.py`) distinguishes symbols defined in this module from external ones: the former uses `adrp`+`add` with `@PAGE/@PAGEOFF`, the latter goes through the GOT (loaded via `@GOTPAGE/@GOTPAGEOFF`) — the standard shape of Mach-O position-independent code. GEP lowering (`emit_gep_offset()`) folds constant indices straight into immediate offsets, handles variable indices with an `lsl` shift or a `mul` by the stride, and requires struct field indices to be constants — anything else is refused.

Global data (`emit_globals()` in `_data.py`) lands in the `__DATA,__const` or `__DATA,__data` section by constness, with initializers expanded recursively: C strings as `.byte` sequences, scalars as `.byte/.short/.long/.quad`, `zeroinitializer` as `.space`, and pointer initializers may be symbol-plus-offset (constant GEPs folded to `.quad symbol+offset`). Structs are padded by `field_offset()` — the layout algebra is the same `TypeDesc` from 13.2, so the data section and the code cannot possibly diverge in their understanding of struct offsets.

### The text peephole layer and the target-pass hook

The price of the slot machine is a flood of "store then immediately reload" redundancy. After assembling all functions, `emit_aarch64_darwin_asm()` runs seventeen peephole passes over the assembly **line list**: adjacent and one-line-apart stack store/load forwarding (`_forward_adjacent_stack_store_load()` and friends), folding zero constants and movs into stores/compares/branches, fusion of the `cset`+branch family (`_fold_cset_zero_branch()` collapses "compare, set, store to slot, test-zero branch" into a `b.cond`), dead `cset` store deletion, trampoline branch threading (`_thread_trampoline_branches()`), flipping conditional branches that fall through, deleting fall-through unconditional jumps, and cleanup of unreferenced empty labels. Every pass is extremely conservative: it touches only scratch registers 9–15 (`_is_aarch64_scratch_reg()`), and its backward scans give up at any label, branch, or call (`_can_drop_zero_mov_after_store()`) — missing an optimization is always preferred to performing a wrong one.

This layer must be kept distinct from the repository's IR Fix Policy (Chapter 12). That policy forbids hiding semantic bugs behind text rewrites because what gets rewritten there is the IR — the contract surface shared by every compiler layer. What gets rewritten here is the self backend's **own freshly emitted output**, every pattern of which was produced by the same emitter (it knows that `[x29, #-N]` can only be its own slot traffic). This is the backend's internal peephole optimization, not a semantic patch. Even so, text peepholes remain a source of fragility, which is why `self_backend_target_passes.py` already lays out the shape of the next step: its module docstring names LLVM 20.1.8's `PassManager.h` and `CodeGenPassBuilder.h`/`TargetPassConfig.h` as the reference for separating IR passes from codegen passes, and it provides `PCC_SELF_TARGET_PASSES` / `PCC_SELF_TARGET_PASS_TRANSPORT` (two transports, `text` or `memory`) plus two registries. What is registered today is only two minimal passes — `strip-trailing-whitespace` on the text side and `verify-prepared-module` on the memory side. This is the honest form of a hook: interface first, leaving room for future target-level IR passes to plug in, rather than growing another layer of text magic.

## 13.5 The x86_64 Linux Subset

`self_backend_x86_64_linux.py` is the second target, and its module docstring opens with the same phrase, "intentionally narrow and explicit": scalar integer/pointer arguments and returns, `alloca`/scalar `load`/`store`, integer binops, direct calls, `ret`. It reuses the entire target-independent layer from 13.2–13.3 (the same parser, the same `prepare_module_for_target()`, the same dispatch skeleton) — proof that the layering is not a paper promise.

Three target-side differences are worth recording. First, syntax: it emits `.intel_syntax noprefix`, so operands carry no `%` prefix — which creates a naming collision that does not exist on the AArch64 side: a global symbol named `ax` or `and` would be read by the assembler as a register or an operator. `_RESERVED_ASM_SYMBOLS` enumerates every colliding name, `_asm_symbol()` prefixes colliding module-defined symbols with `__pcc_sym_`, and a dedicated regression exists (`test_self_backend_x86_64_linux_mangles_reserved_global_symbol_names`). Second, ABI shape: SysV's six GPR argument registers (rdi/rsi/rdx/rcx/r8/r9) and eight xmm registers; aggregates ≤16 bytes go to registers in 8-byte chunks, larger ones go through memory (`_is_memory_aggregate_arg()`) — the same family of rules as the Darwin side, with different parameters. Third, the scratch-register discipline narrows correspondingly to rax/rbx/r10/r11 (`_reg_name()` accepts only the four indices 0/1/10/11; anything else is an immediate `BackendUnavailable`).

Stating the present honestly, as mode labeling demands: in the S-track target matrix, "x86_64 Linux parity" is still an open expansion item; Darwin arm64 is the supported-host default. This subset advances shape by shape through dozens of `test_self_backend_x86_64_linux_*` unit tests in [tests/c/test_self_backend.py](../../tests/c/test_self_backend.py) (phi parallel copies, the vector splat subset, fp calls and returns, ...), with [tests/c/test_self_backend_x86_64_harness.py](../../tests/c/test_self_backend_x86_64_harness.py) as the execution companion. What it can compile today is the set of shapes those tests pin down — not "Linux support is done."

## 13.6 Artifact Shaping and Two Boundary Obligations

### From asm to executable

The C path ([pcc/frontends/c/evaluator/c_evaluator.py](../../pcc/frontends/c/evaluator/c_evaluator.py)) provides three exits: `_emit_compiled_units_self_backend()` supports `--emit-llvm` (IR text), `--emit-asm` (assembly text), and `--emit-obj` (write a temporary `.s`, then `cc -c`); `_run_compiled_translation_units_self_backend()` concatenates the assembly of multiple TUs (stripping each module's trailing `.subsections_via_symbols` line and appending a single one at the end), links with `cc`, and runs directly. When the optimization level is above 0, `_prepare_self_backend_units()` first runs the IR through the repository-managed LLVM optimizer — but recall 13.1: the CLI clamps the self backend's optimization level to 0 by default, so the default path never triggers this step.

The Python bootstrap path ([pcc/frontends/python/pipeline.py](../../pcc/frontends/python/pipeline.py)) is where this artifact chain earns its keep. `_link_native()` picks one of exactly two roads by `_native_backend_kind()`: `llvm` goes to `_link_with_clang()`, `self` goes to `_link_with_self_backend()`, and any other value raises `PyPipelineError` — there is no third road, and no code path of the form "if self fails, try llvm" exists. Inside, `_link_with_self_backend_ir_texts()` takes two forms: a single-module small input runs "host emits assembly, this process drives `cc`"; multiple modules (the normal case in bootstrap) go through `_emit_self_objects_many_via_host_python()` — "emit_self_asm → write `.s` → `cc -c` → `.o`" in parallel up to `jobs`, followed by one `cc` link of all object files plus the runtime archive and `-lm`.

Three details on this path serve the bootstrap fixed point. First, a **content-addressed object cache**: the cache key's SHA-256 ingests the contents of every `self_backend*.py` source file, the environment (`PCC_SELF_TARGET_PASSES` and friends), `cc`, the target identity, and the IR text. Change any line of backend source and the cache invalidates itself — the hardest-to-debug dirty state, "an old backend's `.o` smuggled into a new bootstrap," cannot occur. Second, **deterministic link flags**: on Darwin, `-Wl,-no_uuid` (LC_UUID is the natural enemy of byte comparison), and `-Wl,-dead_strip` when `.subsections_via_symbols` is present. Third, the **publish sequence**: `_finish_self_backend_executable()` first links to `<out>.tmp`; on Darwin it ad-hoc signs with `codesign --force -s -`, runs `codesign --verify` to force the system verifier to observe the final Mach-O, moves into place atomically with `/bin/mv -f`, and finishes with a read-back barrier (the default) or `/bin/sync` (`PCC_SELF_BACKEND_PUBLISH_SYNC=1`, kept for reliability bisection). Every step of this seemingly paranoid sequence corresponds to a real failure — see 13.7.1.

### Obligation one: no silent fallback to LLVM after `--backend=self`

The S-track ([goal-prompt.md](../../docs/goal/goal-prompt.md) §10) makes this one of the first P0 gates: S-P0-A requires that "feeding the self backend an unsupported IR shape must produce a self-backend diagnostic, must not produce a successful artifact, and must not fall back to LLVM." Mechanically the obligation is honored at three layers: the selection layer, with `resolve_backend()`'s explicit opt-in (13.1); the instruction layer, with the omnipresent `BackendUnavailable` (parameterized down to function name and block name); and the link layer, with `_link_native()`'s closed two-way branch and the `PyPipelineError`s raised when `_link_with_self_backend` fails (`"self backend native emission failed"`, `"self backend link failed"`). Why is this discipline worth a P0? Because a silent fallback falsifies all of the S-track's evidence at once: if a bootstrap "passed with the self backend" while three of its modules quietly went through clang, then the byte comparison, the no-libpython scan, and the performance thresholds all measured a mixture. The wording of [AGENTS.md](../../AGENTS.md) obligation 4 — "No silent fallback to LLVM after `--backend=self`" — and the claim-hygiene table's `S-CLAIM_RISK` (LLVM-backed / clang-linked / host-assisted results mislabeled as self-backend completions) say the same thing: falling back is not the sin; the **unlabeled** fallback is.

### Obligation two: the subprocess boundary — do not pull `pcc.backend.*` back into the stage1 closure

The shape of `_emit_self_asm_via_host_python()` looks like a detour at first: write the IR to a temporary `.ll`, spawn a subprocess (`_host_python_command()`: the interpreter named by `PCC_HOST_PYTHON`, defaulting to the `.venv` interpreter and then `python3`), have it execute an embedded code string `_SELF_BACKEND_HOST_CODE`, and let **that** process do `from pcc.backend.self_backend_dispatch import emit_self_asm` and perform the emission — the first line of stdout carries back the target identity, the rest is the assembly. Why not just import in-process? The "Subprocess vs in-process boundaries" section of [AGENTS.md](../../AGENTS.md) states both the prohibition and the reason: `pipeline.py` itself gets compiled into pcc1; if it imported `pcc.backend.*` in-process, those modules would enter stage1's compilation closure, and they (along with the host capabilities required to parse them) would drag the `py_cpy_*` compatibility layer back into the closure — breaking the no-libpython boundary at the root. The subprocess severs "the interpreter that runs the backend" from "the compiler being compiled": all the stage1 closure contains is the small fragment "write a file, spawn a subprocess, read the result," and that fragment is already supported under no-libpython.

This boundary is simultaneously a point that demands honest mode labeling: today, when pcc1 performs native emission, the assembly logic is pcc's but the interpreter running it is the host's — "host-emitted, self-backend-owned." The same [AGENTS.md](../../AGENTS.md) section states the long-term goal: compile those backend modules themselves to native code, rather than expanding in-process CPython fallback in the other direction. In other words, the subprocess boundary is a **directional** transitional form: the direction is to absorb the backend into the closure, not to ossify the host dependency.

## 13.7 History and Lessons

### 13.7.1 The Mach-O stage publish race: producing a binary is not enough — own the "publish" semantics (2026-05)

**Symptom** ([docs/investigations/self-backend-mach-o-stage-publish-race.md](../../docs/investigations/self-backend-mach-o-stage-publish-race.md)): during backend #4 GC work, a long-green bootstrap gate began regressing intermittently — stage2 had just linked `pcc2`, stage3 executed it immediately, and roughly 0.2 seconds in it died with SIGSEGV (exit 139). The same `pcc2`, **re-run after the failure, succeeded**; run under LLDB, it also succeeded.

**Wrong hypothesis**: a Python-frontend semantic bug. The evidence chain rejected it: a stable semantic error does not "heal on re-run," and the failure point sat exactly on the boundary "a freshly linked Mach-O is exec'd immediately." The real root cause was macOS arm64 loader/signature state: the linker writes the final path directly, the file contents are in place, but its executable/signature state is not yet stable for an exec arriving immediately afterward. The fix was layered on incrementally, with each layer proven insufficient by a subsequent failure: first `.tmp`+`mv` atomic rename — not enough; add `codesign --force -s -` ad-hoc signing — reduced but did not eliminate; add `codesign --verify`, forcing the system verifier to observe the final file first — two consecutive rounds passed. Along the way there was a constraint interlock worth recording: an attempt to implement the atomic rename with `os.replace()` was **rejected** by the strict bootstrap, because it introduced a new fallback into the no-libpython closure — the publish sequence may only be built from the already-supported subprocess boundary (`/bin/mv`, `/usr/bin/codesign`).

**The story does not end there.** The 2026-05-15 Update records: after `codesign --verify`, a stage3 crash recurred, and the crash report pointed at `py_decref` — possibly a different class of problem (a generated-code cleanup path) stacked on the same symptom as the publish race. The follow-up continues in `self-bootstrap-reliability-performance-2026-05-15.md`: adding `/bin/sync` passed two rounds, but a global sync introduces host-level I/O variance (part of the suspicion for the gate drifting from about 55 seconds to over 80), so the default was finally switched to a read-back barrier on the signed file, keeping `PCC_SELF_BACKEND_PUBLISH_SYNC=1` for bisection. The same investigation also confirmed a genuine performance root cause: generated code called `pcc_thread_safepoint()` directly at every loop and function gate; changing this to load an exported flag plus a slow-path call brought the gate from 82.30 seconds down to about 71.

**Invariants left behind**: a backend that produces executables must own the **publish** semantics, not just byte correctness; for nondeterministic failure classes, "passed twice in a row" is not closure evidence (the investigation wrote this into its Next Steps verbatim: timing and crash-rate measurement first, optimization talk later); and when fixes are stacked, each layer must record separately what it ruled out.

### 13.7.2 `{ i64` — one comma's splitting policy, and the value model pushing the backend to grow (2026-06-04)

**Symptom** ([docs/investigations/self-backend-valueclass-aggregate-call-signature.md](../../docs/investigations/self-backend-valueclass-aggregate-call-signature.md)): during value-class V2 boundary work, a boxed `Point` retrieved from a container by subscript and passed into a typed function made strict no-libpython bootstrap emission fail:

```text
BackendUnavailable: self backend does not understand LLVM type '{ i64'
```

**Evidence chain**: three hypotheses, each run to a verdict. "Valuebox unboxing produces malformed IR" — rejected; the IR was legal text. "The self backend's aggregate ABI cannot pass small payloads" — rejected; direct nested value-class aggregate smoke tests had long passed, and the failure occurred before target ABI lowering. "`_parse_call_signature()` splits signatures on bare commas" — confirmed. The aggregate parameter in an explicit call signature `call i64 ({ i64, i64 }) @...` was torn at its field comma into `{ i64` and `i64 }`, and the first half, fed into `_parse_type()`, was rejected on the spot. The fix was one line: use the `split_top_level()` from 13.2, aligning with the existing policy on every other parser path. Two focused regressions (parser-level and end-to-end value-class-level) plus a full five-GC bootstrap (458.24 seconds, 5 passed) sealed it.

A sibling investigation from the same day (`self-backend-nested-valueclass-payload-aggregate-return.md`) shows the larger picture of the same driving force: once the frontend began lowering non-recursive nested value-class payloads as literal nested structs `{ { i64, i64 }, { i64, i64 } }`, the self backend's parser failed in sequence at four boundaries — function-header return types, `ret`, `extractvalue`, and aggregate-returning calls. The fix upgraded the narrow regexes to "keep the regex fast path + add a structure-aware fallback" parsing. The investigation's Report section makes a point of stressing that the parser change is **generic over literal nested aggregates, with no special case for value classes** — obligation 3 (generic mechanism) showing up inside the backend.

**Invariants left behind**: the splitting discipline of a textual IR parser is a single global policy, not a per-call-site choice — the whole reason `split_top_level()` exists is to forbid a second comma semantics; the self backend's subset does not grow at random — **the value model's ABI obligations (obligation 7: the self backend's aggregate/scalar ABI) are the concrete force pushing it to grow**; and a failure at a backend boundary must first locate "the first failing boundary" (parse? ABI? runtime?) before any code is touched — the verdict order of the three hypotheses above is a record of that discipline being executed.

### 13.7.3 The self backend's binary crashed ≠ the self backend is wrong (2026-05-09, active)

A short but necessary counterpoint ([docs/investigations/stage1-self-backend-ir-scaffold-segfault.md](../../docs/investigations/stage1-self-backend-ir-scaffold-segfault.md), status: active): a pcc1 built with `--backend self` segfaults while compiling stage2. After minimization, the root cause currently points at the **frontend's** method dispatch — `_emit_method_call`'s closed-world "any class declaring this method" fallback wrongly bound `.append(...)` on a `DynType` receiver to `pcc.ir.ir.Block.append`, passing an `ir.Value` to a function expecting a string instruction line. The symptom is signed "the self backend's artifact crashed"; the root cause lives in no line of [pcc/backend/](../../pcc/backend). This is exactly where rule 1 of the [AGENTS.md](../../AGENTS.md) bootstrap regression discipline earns its place: first establish the first failing boundary in mode-labeled language (`pcc0→pcc1` fallback? `pcc1→pcc2` runtime crash?), then list suspect subsystems. In a self-hosting chain, the backend is the final developing fluid for every upstream semantic error — most of the photographs it develops were not taken of itself.

## 13.8 Summary

The question the self backend answers is whether the last link of the fixed point — native emission — can also be owned by pcc. Its answer is deliberately narrow and honest:

1. **Identity**: LLVM's three roles are handled separately — as a library, absent from the bootstrap chain; as an IR dialect, retained as the oracle bridge; as an optimizer, off by default, with opt-in use requiring labeling. `self` carries `supported: False` in `_BACKEND_TABLE`; choosing it is the act of opting into the experimental.
2. **Structure**: a target-independent layer (regex parsing, `TypeDesc` layout algebra, lightweight liveness, everything-spills slot assignment, content-hashed symbol prefixes) + a target registry with two dispatch tables + target emitter families (the full AArch64 Darwin family, a narrow x86_64 Linux subset) + the backend-internal text peephole + the target-pass hook. One stack slot per SSA value buys locality and determinism of emission; part of the quality loss is recovered by seventeen conservative peepholes.
3. **Refusal**: unsupported shapes raise `BackendUnavailable`, from type tokens to icmp condition codes without exception. This is not an apology for incompleteness; it is the implementation material of the S-P0-A gate: silent guessing and silent fallback are two faces of the same lie.
4. **Boundaries**: an artifact counts as published only after system `cc` assembly and linking, and on Darwin after signing, verification, and read-back; after `--backend=self` no code path leads to `_link_with_clang()`; pcc1 runs the backend through a subprocess on the host interpreter, keeping `pcc.backend.*` out of the stage1 closure — a transitional form with an explicit direction.

The three case studies each pin an invariant onto a boundary: publish semantics belong to the backend's correctness surface; a textual parser may have exactly one splitting policy, and what drives the subset's expansion is the value model's ABI obligations; and on a self-hosting chain a crash's signature is untrustworthy — the first failing boundary must be established in mode-labeled language.
