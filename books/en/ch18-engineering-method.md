# Chapter 18: Method — Tests, Investigations, and Claim Hygiene

A compiler book that ends with a chapter on method is not being polite. Most bugs in pcc are not parse errors; they are semantic errors that only become visible when expressions are combined, lowered to IR, and then exercised by real programs — and by then the crash site is usually several subsystems away from the cause. In a system like that, *how you test, how you investigate, and how you state results* is not engineering hygiene bolted onto the design; it is part of the design. The bootstrap fixed point and the five-GC matrix are product features, but they are also the two most important measuring instruments this repository owns. This chapter lays out the written method piece by piece: the gate system and its baseline files, the twelve techniques of the debugging playbook, the evidence-chain discipline of the investigation workflow, the mode-labeling rules of claim hygiene, and three documented incidents of false confidence in measurement. Everything here is grounded in real files: [AGENTS.md](../../AGENTS.md), [docs/debugging-playbook.md](../../docs/debugging-playbook.md), [docs/investigation-workflow.md](../../docs/investigation-workflow.md), [goal-prompt.md](../../docs/goal/goal-prompt.md), and the investigation records under [docs/investigations/](../../docs/investigations).

## Chapter Overview: Method Protects Claims

This chapter is not extra process. It is the protection layer that lets the previous design claims hold. Every major pcc goal has a tempting local success that can be misread, so mode labels, minimized reproducers, real-project confirmation, and baseline gates keep the claims pinned down.

- Tests are not better just because there are more of them; they need to cover the semantic boundary that changed.
- Investigation docs are not after-the-fact paperwork; they prevent the same failure class from being guessed at repeatedly.
- Claim hygiene has a practical purpose: readers can see exactly what a result proves and what it does not prove.

## 18.1 The Problem and the Design Space: Why Method Is Part of the Design

Start with the actual working conditions of this repository. First, causal chains are long: a stage2 segfault can be rooted in a per-name cache that one frontend code path forgot to reset on the generator branch (Chapter 9, second case study); a flaky failure in Lua's sort can be rooted in an `^` expression that dropped its unsignedness metadata (Section 18.7). Second, the working tree is shared by multiple agents and humans; chat logs evaporate, and "what the previous person already ruled out" is precisely the most expensive information to lose. Third, claims about a system like this drift naturally: the same sentence "X is supported" can mean eight different things depending on whether it was observed under host pcc or pcc1, libpython or no-libpython, the LLVM backend or the self backend.

The design space offers three kinds of answer. One: **rely on scale** — run the full test suite on every change. The full suite here takes minutes and the bootstrap gates take hundreds of seconds; making that the inner loop collapses iteration speed, and a green full suite still cannot answer "in which mode does this claim hold." Two: **rely on people** — senior maintainers' memory and review. With parallel agents and disposable sessions, memory is not a storage medium. Three: **reify the method into repository artifacts** — state goes into testable JSON baselines, history goes into structured investigation files, honesty goes into a citable claim-hygiene table, and procedure goes into mandatory sections of [AGENTS.md](../../AGENTS.md). pcc chose the third option, and chose it thoroughly: the comment block of [tests/bootstrap_gate_baseline.json](../../tests/bootstrap_gate_baseline.json) declares itself the authoritative state for Issue 1, and [AGENTS.md](../../AGENTS.md) states in so many words that these JSON files are the source of truth while historical tracker documents may lag.

From this standpoint, two things that look like product features turn out to be measurement devices first:

**The fixed point is a whole-system differential test.** The chain `pcc0 -> pcc1 -> pcc2 -> pcc3` requires the compiler to reproduce itself: an inconsistency anywhere — semantics, runtime, code generation, object model, backend, diagnostics — surfaces as divergence between stages. [AGENTS.md](../../AGENTS.md) says it outright: the fixed point "is more than a byte compare"; it is evidence that the subsystems are coherent. As a test, it has a property no unit test has: its input is the entire compiler itself, so every "only shows up on large programs" semantic bug is inside its blast radius. And the criterion is deliberately non-negotiable — pcc2 and pcc3 must be byte-identical after Mach-O signature normalization ([tests/bootstrap_gate_baseline.json](../../tests/bootstrap_gate_baseline.json)). Differences may not be patched around, only *classified*: semantic / IR-text / class-layout / object-model / backend nondeterminism / link metadata / perf-only / diagnostic ([AGENTS.md](../../AGENTS.md), obligation 5).

**The five-GC matrix is five independent observers of one contract.** The five backends (refcount+cycle, incremental, concurrent, generational, relocating) all consume a single slot-based trace/update contract (`py_obj_visit_slots` / `py_obj_update_slot` plus root, frame, and native-handle registration). The Production Equality Rule ([goal-prompt.md](../../docs/goal/goal-prompt.md), G-track) forbids any backend from winning by weakening finalizers, weakrefs, resurrection, suspended coroutine frames, or value payloads. The consequence is that every object-graph mistake gets five chances to be caught by five different algorithms: a GC root the frontend forgot to register may be masked by reference counting on backend #0 and become a dangling pointer immediately under backend #4's relocation. `tests/python/gc/test_pcc_bootstrap_full_gc{0..4}.py` — one file per backend, each running the full three-stage bootstrap — is the wiring that connects this instrument to the fixed-point instrument.

That is the position of this chapter: method is not scaffolding around the design; it is the design extended. The remaining sections are the operating manual for this instrument cluster.

## 18.2 The Gate System: Baselines as State

The Testing & Definition of Done section of [AGENTS.md](../../AGENTS.md) gives the minimum four steps for any semantic fix: add a focused regression test; confirm the original realistic reproducer is fixed; run the focused gates covering the touched subsystem; and for anything commit-level, pass the bootstrap gates. The Definition of Done is a checklist: smallest reproducer passes, original integration scenario passes, temporary debug edits removed, regression test exists in [tests/](../../tests), focused gates pass (and if the full suite is skipped, you must say exactly which subset ran and why it suffices), and the required bootstrap validation ran. Note the rhetoric: the full suite is *optional by default*; the focused gates are *mandatory*. That is an explicit rejection of the rely-on-scale route, and its price is that every change must first answer "which subsystem did I touch, and which are its sensitive gates."

Gates come in layers. Innermost are **focused regressions** — [tests/c/test_unsigned_loads.py](../../tests/c/test_unsigned_loads.py) for signedness, [tests/python/test_return_ownership.py](../../tests/python/test_return_ownership.py) for return ownership. The middle layer is **subsystem gates**; [AGENTS.md](../../AGENTS.md) lists them for high-risk paths: Lua compile-and-runtime comparison, SQLite integration, `llvm_capi` parity against `llvmlite`, and so on. The outermost layer is two **repository-level contract gates**, whose common trait is that they assert against *state files* rather than behavior:

```text
tests/bootstrap_gate_baseline.json   authoritative bootstrap state: no stage
                                     links libpython; pcc2/pcc3 (after signature
                                     normalization) byte-identical must remain true
tests/fallback_baseline.json         no-libpython fallback ratchet: multi-file
                                     fallback totals are zero and must stay zero;
                                     per-module counts remain a diagnostic ratchet
                                     against dynamic-idiom creep
```

The corresponding tests are [tests/python/test_bootstrap_gate_baseline.py](../../tests/python/test_bootstrap_gate_baseline.py) and [tests/python/test_fallback_baseline.py](../../tests/python/test_fallback_baseline.py) / [tests/python/test_ir_py_fallback_baseline.py](../../tests/python/test_ir_py_fallback_baseline.py):

```python
# tests/python/test_fallback_baseline.py
def test_fallback_baseline_ratchet():
    baseline = json.loads(pathlib.Path("tests/fallback_baseline.json").read_text())
    current = count_fallback_routes()
    assert current <= baseline["max_allowed_fallbacks"]
```

At the task board level, [scripts/goal_state.py](../../scripts/goal_state.py) enforces schema validation:

```python
# scripts/goal_state.py
def validate_task_board(board_path: str = "docs/goal/task-board.yaml") -> int:
    tasks = load_tasks(board_path)
    for task in tasks:
        validate_task_schema(task)
    print(f"OK: {len(tasks)} tasks validated")
    return 0
```

At the test infrastructure layer, [tests/conftest.py](../../tests/conftest.py) isolates environment and cache states via an autouse fixture:

```python
# tests/conftest.py
@pytest.fixture(autouse=True)
def _isolate_env_and_caches(tmp_path_factory):
    old_env = os.environ.copy()
    yield
    os.environ.clear()
    os.environ.update(old_env)
```

The word *ratchet* deserves a pause: such a gate does not assert a fixed value, it asserts **monotonicity** — current fallback counts may not regress past the baseline. It turns "progress" itself into a regression-testable quantity; any change that lets the fallback surface creep back is caught mechanically, with no reliance on a reviewer remembering last month's numbers.

Above the gates sits a grading of claim strength. [goal-prompt.md](../../docs/goal/goal-prompt.md) §0.1 lists the full preconditions for `DONE_STRONG`: the implementation must be a generic mechanism rather than a hard-coded special case; there must be a focused regression plus a negative or boundary test; pcc1 claims need no-host evidence at the level of `PCC_HOST_PYTHON=/bin/false`; claims touching runtime/GC/rooting/object lifetime need *all-five-GC* bootstrap evidence — passing on backend #0 alone is not a strong claim; performance claims need an IR-shape gate plus a runtime benchmark. §0.2 then fixes the evidence format: commands written in full and reproducible; if a test was not run, write `not run` with a reason; **"should pass" is forbidden**. Any completion summary for a slice touching pcc1, the self backend, no-libpython, runtime/GC, or shared lowering must carry an explicit line of the form `bootstrap: passed|failed|not run` — omitting that line is itself a validation gap.

## 18.3 The Debugging Playbook: Twelve Techniques

[docs/debugging-playbook.md](../../docs/debugging-playbook.md) is task-conditionally mandatory procedure: the moment you are debugging a failure, read it before guessing. The twelve techniques carry stable numbers (§1–§12) and are cited directly by [AGENTS.md](../../AGENTS.md) and by investigation files. Here they are one by one, each with its anchor in the repository.

**§1 Make the failure deterministic first.** Do not start by reading all of `c_codegen.py`. Fix the random seed, replace filesystem/time inputs with constants, run with `-n0` so xdist cannot hide ordering or temp-file effects, isolate one test file. If the failure is random, removing the randomness *is* the first job. In the sort.lua case study of 18.7, the first effective move was `math.randomseed(15)`, not reading code.

**§2 Use a same-source reference to separate "the program is odd" from "the compiler lowered it wrong."** The C side compares against the system C compiler; the Python side against CPython; `llvm_capi` against `llvmlite`; bootstrap stage divergence against the two JSON baselines. Same source, two toolchains, different behavior — only then does the bug belong to the compiler.

**§3 Use `llvmlite` as an oracle for `llvm_capi`.** `PCC_USE_LLVMLITE_C=1` swaps the IR-builder implementation under the same minimized repro; compare compile results, runtime results, and if necessary the emitted IR. It is especially effective for missing `IRBuilder` operations, constant `gep`/`bitcast`, and opaque-pointer semantics. It is *not* an oracle for the preprocessor, fake-libc, or parser acceptance — if both backends fail the same repro, the bug is above the backend layer.

**§4 Treat short fallback/IR traces as locators only.** Before naming a root cause you must confirm four things: the enclosing `define` function, the actual `py_cpy_*` call instruction, the source of the helper argument, and the source expression that produced it. With only short context available, the verdict must be written as "candidate, unconfirmed." This is a standing prohibition against patching shared lowering off two lines of trace.

**§5 Shrink the reproducer in stages.** Failing integration test → smaller script/input → small harness calling the same internal code path → pure C/Python expression. Time spent shrinking is repaid many times over.

**§6 Test hypotheses by substitution, not only inspection.** Copy the suspect function into a temporary harness, swap real helpers back in one at a time, reintroduce branches incrementally. Often faster than staring at five hundred lines of IR.

**§7 Avoid harness mistakes — they look like compiler bugs and are not.** This technique is a casualty list: pytest node ids with `[`/`]` must be quoted in zsh; macOS `multiprocessing` spawn is incompatible with `uv run python - <<'PY'` heredocs; manifests drift, so re-run through the *current* harness before debugging pcc; after changing grammar or lexer token sets you must bump the PLY cache version in [pcc/frontends/c/parse/c_parser.py](../../pcc/frontends/c/parse/c_parser.py), or the stale `yacctab` makes the fixed parser look still broken; a long run without its final summary is not a result. What unites these mistakes is that their symptoms are indistinguishable from compiler bugs.

**§8 Use LLDB for native crash triage, not guesswork.** Answer two questions: which generated/project function first received invalid data, and what runtime object the bad pointer actually points to. Batch mode, hard timeouts, never stop at the top runtime frame (a crash inside `py_str_strip` usually means the *caller* passed a bad object), and decode the *object* rather than the address by checking offsets against `py_runtime.h` — the type tag lives at `obj + 8`. LLDB localizes; the fix still needs a minimized regression test.

**§9 Do not stack unverified edits in shared codegen.** [pcc/frontends/c/codegen/c_codegen.py](../../pcc/frontends/c/codegen/c_codegen.py) and the lowering mixins under [pcc/frontends/python/codegen/](../../pcc/frontends/python/codegen) are shared by almost every meaningful path; one "small local cleanup" can break Lua, SQLite, and GC backends at once. The rules: changes not backed by a minimized reproducer stay in a scratch probe, not the repository; after every shared-path edit, run focused regressions *before* the next edit; if the first fix attempt does not clearly improve the minimized reproducer, stop expanding the patch and go back to reduction.

**§10 Separate data-layout bugs from expression-semantics bugs.** For layout suspicions, build a `sizeof`/`offsetof` probe and compare native versus pcc; once layout matches, that whole class of hypotheses is gone. What remains is signedness, promotions, comparisons, shifts — semantics. Falsify the big class first, then descend.

**§11 Prefer downstream-sensitive regression tests.** A good test places the expression in a context where the *next* operation would be wrong if semantic metadata were lost: an unsigned expression immediately followed by `%` with a signed constant, by `>>`, or by a comparison. LLVM's integer types do not distinguish signedness, so the compiler must carry the intent itself; tests that only assert bit values cannot catch that loss.

**§12 Treat compile-time constant folding as a semantic subsystem.** Integer semantics live in two places: runtime IR lowering and compile-time evaluation in `_eval_const_expr()`. Fixing only the runtime path is not enough — `((size_t)(~(size_t)0))` can fold to `-1`, and a real project then compiles with the wrong constant and fails far away.

Taken together the twelve form an ordering: make it deterministic (§1), attribute it (§2/§3), shrink it (§5/§6) while refusing to be misled by harnesses (§7) and short traces (§4), respect shared-path discipline when editing (§9), separate layout from semantics when fixing (§10/§12), lock it down with downstream-sensitive tests (§11), and hand native crashes to LLDB (§8).

## 18.4 The Investigation Workflow: Evidence Chains as Repository Artifacts

Anything more involved than a one-line fix requires a written investigation. [docs/investigation-workflow.md](../../docs/investigation-workflow.md) gives the justification in concrete terms: the structure costs about ten minutes per investigation, and skipping it has cost this project literal *weeks* of duplicated diagnosis — a second agent re-deriving a first agent's findings because the original never got a `## Status` line.

The mechanics are light. One investigation = one file under `docs/investigations/<specific-slug>.md`, and the slug must be specific (`pcc1-stage2-lift-expr-raw-value-leak.md`, not `bug.md`). Before opening a new file, scan [docs/investigations/INDEX.md](../../docs/investigations/INDEX.md) — a topic-grouped index with one-line summaries; if the symptom matches an existing entry, continue it via an `## Update` block or link it as predecessor from the new file. After adding or editing any investigation, regenerate the index with [scripts/regen_investigations_index.py](../../scripts/regen_investigations_index.py). Existing files are historical record and are never deleted or rewritten; superseding a finding means linking the old file and adding `## Status: superseded by <doc>` to it.

The mandatory sections form the skeleton of an evidence chain: `## Status` (active / resolved / superseded); `## Problem Description`; `## Repro` (the smallest deterministic command sequence, including expected exit code or backtrace marker); `## Test [CONFIRMED|N/A]`; a `## Proposals` list, each proposal expanded into `### Code Change` plus `### CONFIRMED|DENIED|DENIED BY USER`; and a closing `## Report`. Three modes cover every entry point: **Repro** (fresh problem — do not stop until `## Test [CONFIRMED]` has been *observed*), **Continue** (append `## Update`; never rewrite history), **Report** (closing summary; never delete the proposals that turned out wrong — their `### DENIED` paragraphs are the record of what was ruled out).

Four hard rules, each blocking a specific kind of rot. **One proposal at a time**, run to a verdict; if no verdict is reachable, write `### DENIED — incomplete` with the open question and stop — this blocks the confusion of "tried three changes at once, it went green, no idea which one did it." **Test = observation, not optimism** — `[CONFIRMED]` may only be written after the failure was seen under the listed command — this blocks "I'm sure it would fail." **Two distinct bugs → two files** — this blocks one report carrying two storylines. **Status is final** — once resolved or superseded, the body is not edited again — this blocks retroactive grooming of history.

Whether the template earns its keep is best judged on an instance. [docs/investigations/pcc1-stage2-lift-expr-raw-value-leak.md](../../docs/investigations/pcc1-stage2-lift-expr-raw-value-leak.md) is a textbook evidence chain, worth dissecting section by section.

The symptom: pcc1 compiling stage2 throws `AttributeError: object has no attribute __name__` inside `lift_expr`. The file's first move is to split the secondary failure from the primary one: the `__name__` error is just the fallback `raise` blowing up; the primary failure is whatever made dispatch fall through. Next comes diagnostic instrumentation: the raise clause is temporarily expanded to `isinstance`-test all 25 expression node classes and to detect raw Python primitives — and the observations from three separate runs are recorded *as a table* (the leaked values: the string `"'"`, a raw tuple, the string `"{"`). Then a section literally titled "What this rules in / out": not a missing dispatch case (`isinstance` is false for all 25 classes); not a double-import class-identity bug (that would break `is` but `isinstance` would still match); not the host-side parser (under CPython hosting the same lifter never trips). Then the methodologically most interesting scene: the *second* layer of instrumentation — writing a statement trail into `self.<attr>` — makes pcc1 segfault outright. The investigation does not fold this into the main storyline; it explicitly records it as a *separate pcc-py codegen bug surface*, reverts that instrumentation, and switches to a locals-only variant. The net closes: a table of failing statement indices and line numbers across five runs shows every failure landing in the *only seven* `@classmethod`/`@staticmethod`-decorated methods of the Parser class — the failure window maps exactly onto the decorator region. Root cause: `_parse_decorated` does `fn.decorators = list(decorators)`, a post-construction mutation of a dataclass field whose default is `None`; pcc1's runtime setattr path corrupts a neighboring slot in that shape. Passing decorators through the constructor makes the bug vanish. The file closes its accounts honestly: the source-side refactor is the workaround that landed; the deeper runtime setattr bug remains real and is listed as follow-up; and a further `--verbose`-sensitive segfault downstream is *not merged into this case*.

That one file demonstrates every element of an evidence chain: observations archived as tables, exclusions argued rather than asserted, instrumentation that itself misbehaves filed as a separate case, root cause separated from workaround, residue explicitly handed off. The next agent needs no chat log.

## 18.5 Claim Hygiene: The Mode Is Part of the Proposition

One of pcc's seven obligations reads "compatibility must be mode-labeled." It is operationalized by the claim-hygiene table in [goal-prompt.md](../../docs/goal/goal-prompt.md) §0.10 — eight lines, worth quoting whole:

```text
host pcc pass          != pcc1 pass
cpython-compat pass    != pcc-native pass
libpython mode pass    != no-libpython pass
fake package pass      != real package pass
array-core pass        != import numpy pass
stage1 self-backed     != pcc1->pcc2->pcc3 self-backed
metadata exists        != runtime implementation complete
microbenchmark win     != whole-program performance win
```

Each line is a pair of propositions that are routinely conflated. Frontend code that runs under CPython hosting is not the same proposition as the compiled pcc1 binary running it (the execution boundary is entirely different — the second case study of 18.7 is a chapter-length testimony); an extension accepted in compat mode is not accepted by the pcc-native ABI; stage1 emitting itself through the self backend is not the same as the artifact reproducing itself for two more generations. §9.2 accordingly requires every claim to name its mode: pcc-native / cpython-compat / libpython / host-only diagnostic / pcc1 no-host / self-backed / LLVM-backed.

Claim hygiene constrains more than wording; it constrains the shape of code and tests. Performance claims (§9.5) must carry, simultaneously: IR-shape evidence (e.g. no `pcc_gc_alloc` in the hot loop, no `py_cpy_*`, no `py_obj_call` in a typed loop), a runtime benchmark, a slow-path/guard correctness test, and a CPython baseline — a lone microbenchmark win claims nothing. Package claims ([AGENTS.md](../../AGENTS.md), Package/NumPy Claim Hygiene) make install and import two separate gates; a synthetic package or an array-core-only test does not constitute a NumPy support claim. And package-name special cases — `if package == "numpy"` — are banned outright: the generic mechanism (install/import/ABI/buffer/capsule) must be fixed and regression-tested. A special case can turn a gate green, but it quietly substitutes "supports a string named numpy" for "supports NumPy," which is precisely the forgery claim hygiene exists to stop. The end-state claim has its own standard in §19.2: "pcc1 can replace python" may be claimed only when no-host execution, the linkage scan, the deterministic pcc2/pcc3 compare, no silent LLVM fallback, the semantic differential, real-package evidence, five-GC mutual non-regression, and the full performance evidence set are present *at the same time*; with anything missing, write only partial progress and open blockers.

What this table means in practice is demonstrated repeatedly by 18.6 and by the second case study of 18.7: nearly every recorded episode of false confidence is someone taking the left-hand side of one of those eight lines for the right-hand side.

## 18.6 Regression and Measurement Discipline

**Regression discipline.** When a long-green gate regresses, [AGENTS.md](../../AGENTS.md) requires a causality audit before any fix narrative, in a fixed order: (1) identify the first failing boundary in mode-labeled terms (`pcc0 -> pcc1` fallback, `pcc1 -> pcc2` runtime crash, `pcc2/pcc3` byte drift, …); (2) before changing more code, list the recently touched subsystems that could plausibly own that boundary — for codegen/runtime changes, your own recent change is the prime suspect until IR/source/debugger evidence rules it out; (3) separate stacked failures: if fixing the first boundary exposes a second crash, write them as two failures with two evidence chains, never collapse them into one guessed root cause; (4) never weaken runtime or GC semantics to localize a failure — disabling GC tracking, barriers, owned-local cleanup, or finalizers is a semantic change, not a diagnostic; (5) for ownership failures, verify the caller/callee reference contract before touching cleanup code; (6) host-side tests are not bootstrap proof — fixes touching frontend/runtime/bootstrap entry points need a focused regression plus the appropriate bootstrap gate; (7) debug instrumentation must be tagged, recorded in the investigation, and removed or promoted to a deliberate tested feature before finishing. Rule (3) has its best demonstration in the 18.4 case study; rule (4) was once enforced by the user personally, vetoing a proposal to disable tuple GC tracking (Chapter 9's ownership case study).

**Measurement discipline.** Gates and baselines are only meaningful while their preconditions hold; with a broken precondition, green is more dangerous than red. The repository carries three documented false-confidence incidents, each of which left behind an invariant:

*Incident one: a stale cache manufactured a false "gap 0" (2026-05-29).* [docs/investigations/python-no-libpython-numpy-build-pcc-capi-include-redirect.md](../../docs/investigations/python-no-libpython-numpy-build-pcc-capi-include-redirect.md) contains a self-correction section: the previously announced "full-module host C-API link gap = 0" milestone had been measured against a **stale** `/tmp/pcc_capi/Python.h`. The stale header failed to compile 38 files, so those files' host-symbol references *never entered the measurement at all*. Re-measured against a directory refreshed from the current [utils/fake_libc_include/](../../utils/fake_libc_include): compilable files rose from 60 to 95, and the real gap was 10 symbols, not 0. Invariant: refresh the measurement substrate before measuring; missing members of the measured set are themselves a measurement error.

*Incident two: `PCC_RUNTIME_CC=cc` pinned the oracle path (2026-05-30).* [docs/current-goal-state.md](../../docs/current-goal-state.md) records a starred critical correction: the *default* runtime mode links the pcc-Python ports (the Makefile `PY_MODULES` list — `py_dunder`, `py_str_accessors`, `py_set`, and others), while the session's regression tests had all set `PCC_RUNTIME_CC=cc`, which links the C sources. The tests therefore validated only the cc oracle path and **masked** the actual goal mode. The consequence was concrete: a default-mode program calling `bin(5)` failed to link with `undefined _py_builtin_bin` (the port lacked the new symbol) while the same program worked in cc mode; four slices "passed bootstrap" only because pcc's own code never exercises those features. The fix was the rule [AGENTS.md](../../AGENTS.md) had stated all along — mirror every C runtime change into its pcc-Python port — plus re-validating the tests in default mode. Invariant: tests must run in the mode the claim names; testing a goal-mode claim in oracle mode is one more row of the §0.10 table.

*Incident three: reading a buffered log mid-run misdiagnosed a successful bootstrap (2026-05-29).* Also in [docs/current-goal-state.md](../../docs/current-goal-state.md), the entry that landed the ob_type bridge carries a paragraph explicitly labeled as a diagnostic-honesty note: the author first **misread** the bootstrap as failing — premature reads of the buffered log and build directory while the ~54-second run was still mid-stage2, with a trailing `;ls` masking the real exit code — and reverted a correct change on the misread; a clean re-run showed the byte-identical verify, and the change was re-applied. The recorded lesson: read bootstrap results only after the task completes, from the full log's `verify:` line plus the bootstrap's own exit code, never from premature artifact checks.

The three incidents are isomorphic: the measurement action itself was correct; a *precondition* — cache freshness, mode correctness, run completion — was silently violated. This is why §0.2 demands evidence in the form of full commands: a reproducible command makes the preconditions explicit, giving the next reader a chance to notice that one of them is broken.

## 18.7 History and Lessons

### Case study one: sort.lua's flaky failure and the lost unsigned semantics

(Source: [docs/investigations/lua-sort-random-pivot-signedness.md](../../docs/investigations/lua-sort-random-pivot-signedness.md).)

Symptom: `tests/test_lua.py::test_pcc_runtime_matches_native[sort.lua]` failed intermittently — pcc-compiled `onelua.c` exited nonzero where the natively compiled binary passed. Same source, different behavior: the bug belonged to the compiler first (§2). The surface candidates were a full lineup — stack corruption, aggregate copy, struct layout, the comparator, the Lua runtime — and every one of them turned out wrong.

Each step of the investigation maps back onto the twelve techniques. Step one, determinism (§1): seed the generator with `math.randomseed(15)`, construct deterministically failing array shapes, and compress "sometimes fails" into "reversed input + custom comparator + minimum failing size around 1921." Step two, a smaller harness that keeps the real implementation (§5): `#define main pcc_onelua_main`, `#include "onelua.c"`, build a table, call the real internal `auxsort` directly — native passes, pcc fails deterministically. Step three, falsify the big hypothesis classes fast (§10): a `sizeof`/`offsetof` probe shows `TValue`, `lua_State`, and friends laid out identically to native, eliminating layout; a stack-shape probe clears `luaL_makeseed`; piecewise substitution (§6) shows `sort_comp` and `partition` are innocent — they only misbehave after an earlier mistake has violated quicksort's invariants. Step four, substitution-bisect onto the random-pivot path: a derandomized `auxsort` passes, a tiny fixed `rnd` passes, a large real `rnd` fails. Step five, reduce to pure C (the endpoint of §5): the `choosePivot` formula `(rnd ^ lo ^ up) % (r4 * 2) + (lo + r4)` with `lo=1, up=1921, rnd=3426782842u` yields 731 natively and 475 under the old pcc.

The wrong value 475 was itself evidence: it sits exactly 6 below the legal lower bound 481 — the signature of a signed remainder. Interpreted unsigned, the formula gives a legal pivot; interpreted as signed 32-bit, the remainder is -6. The root cause lands in [pcc/frontends/c/codegen/c_codegen.py](../../pcc/frontends/c/codegen/c_codegen.py): pcc lowers both signed and unsigned 32-bit integers to LLVM `i32`, carrying signedness in separate metadata (`_tag_unsigned` / `_is_unsigned_val`), and `^` returned `builder.xor(...)` without re-tagging the result as unsigned when the C result type was unsigned — bits all correct, semantics already lost, and the next `%` compiled to `srem`. After the fix, auditing the neighboring operators in the spirit of §10 caught a second genuine bug of the same family: unsigned prefix `++`/`--` expression results were also not re-tagged.

The invariants left behind operate on two levels. Mechanism level: `^`, unsigned `>>`, integer compound-assignment results, and unsigned prefix increment/decrement all preserve the unsigned tag, with regressions in `tests/test_unsigned_loads.py` — all deliberately written in the "unsigned result immediately feeding `%` with a signed constant" shape (§11). The repository did not lack unsigned tests before; it lacked exactly that shape, which is why an entire bug class stayed invisible. Process level: the investigation's template — native reference first, derandomize, minimal integration harness, separate layout from semantics, reduce to pure C, inspect metadata propagation rather than arithmetic instructions — was distilled into the C Codegen Invariants section of [AGENTS.md](../../AGENTS.md) and into the playbook itself. A substantial fraction of the method documents' content was condensed out of case studies in precisely this way.

### Case study two: the runtime semantic holes exposed by the no-libpython self-host

(Source: [docs/investigations/python-self-host-no-libpython-runtime-holes.md](../../docs/investigations/python-self-host-no-libpython-runtime-holes.md), reporting as of 2026-04-29.)

Issue 1's literal target is simple: the bootstrap binary must not link libpython. The report's central finding is that **criteria can lie**. Building with `--python-libpython off` succeeded and `otool -L` showed no libpython — and with those first two criteria passing, the third and fourth (run the artifact as a compiler; have it compile a tiny program into a working binary) still exposed a field of self-hosting bugs. A `py_cpy_*` count of zero is necessary, not sufficient: the count proves there is no fallback to CPython, but says nothing about whether pcc's own runtime implements the Python behavior the compiler's source relies on — class attribute storage, descriptor behavior, the side-effect count of chained parser helper calls are all in the count's blind spot.

The methodologically heaviest hole in the report is the origin of the exception-model section in [AGENTS.md](../../AGENTS.md): pcc has no Itanium-style unwinding; `py_raise(exc)` stores the exception in TLS and returns normally, and generated code must check `py_err_occurred()` after any call that may raise. The top-level bootstrap path at the time missed a link in that chain: an internal compile-time exception propagated to the function's error epilogue, returned a sentinel integer, `bootstrap_cli_sys_argv_exit()` saw 0 — and **the process exited successfully with the compilation failed and no artifact produced**. "Compile succeeded with no output" was not an isolated bug but a failure *shape* the criteria let through, visible only by breaking on `py_raise` in LLDB. The report then drew a three-way distinction — compile error (bad user input), compiler execution error (pcc1 itself raised internally), target execution error (the emitted binary failed) — and observed that the behavior of the day collapsed the second category into silent success.

The report's "Why So Many Errors Happened" section is a structural critique of the test pyramid. Nearly all existing tests had the shape "CPython runs pytest → pytest calls pcc frontend code → check the emitted artifact," while the bugs lived in a different shape: "CPython builds pcc1 → pcc1 executes parsing, type inference, codegen, and IR object construction *inside pcc's own runtime, without libpython* → check what pcc1 emits." The conclusion was not "run more tests" but "add the missing layer" — a small, deterministic, mandatory set of stage1-as-compiler gates: a link gate (no libpython linkage, `--help` exits 0); a compile gate (the fresh pcc1 compiles a minimal program whose binary runs); an object-model gate for `llvm_capi.ir` under pcc-compiled execution; a parser side-effect gate (`_expect()` not duplicated by chained attribute access); a module-initializer gate; and an error-propagation gate (an internal exception must produce a nonzero exit, a printed exception, and no leftover artifact). The state guarded today by [tests/bootstrap_gate_baseline.json](../../tests/bootstrap_gate_baseline.json), and the [AGENTS.md](../../AGENTS.md) verdict that a missing `py_err_occurred()` check is one of the three usual suspects, are this report's direct legacy.

Together the two stories give the chapter's thesis its best testimony. The first shows the twelve techniques converging a flaky real-program failure into a two-tag metadata fix plus a family of downstream-sensitive tests. The second shows what method produces when the criteria themselves have blind spots: not a patch, but a **new gate layer and new invariants**. The method documents are not static bylaws; they are iterated by these investigations, alongside the compiler.

## 18.8 Summary

pcc builds its engineering method as part of the design, not as etiquette around it. The fixed point is a whole-system differential test; the five-GC matrix is five independent observers of one slot contract; the two instruments are wired together by `tests/python/gc/test_pcc_bootstrap_full_gc{0..4}.py`. State is reified into testable baselines: [tests/bootstrap_gate_baseline.json](../../tests/bootstrap_gate_baseline.json) holds pcc2/pcc3 byte identity, and [tests/fallback_baseline.json](../../tests/fallback_baseline.json) holds the no-libpython fallback surface monotonically non-regressing, as a ratchet. The twelve playbook techniques form a fixed order — determinize, attribute, shrink, verify by substitution — while refusing the traps of harness artifacts and short traces, never stacking unverified edits in shared codegen, and finishing with downstream-sensitive tests. The investigation workflow turns evidence chains into repository artifacts: one investigation, one file; mandatory sections; one proposal at a time; `[CONFIRMED]` reserved for observed failures; denied proposals kept as the permanent record of what was ruled out. The claim-hygiene table splits eight routinely conflated proposition pairs; the mode label is part of the proposition; the `DONE_STRONG` bar and the mandatory `bootstrap:` line write evidence strength into the process itself. Three documented measurement incidents — the stale header's false "gap 0," `PCC_RUNTIME_CC=cc` pinning the oracle path, the mid-run buffered-log misread — point at one meta-rule: a measurement's preconditions must be stated and checked along with the measurement. Every piece of this discipline was paid for by a specific incident. That is what earns it a place in a book about design.
