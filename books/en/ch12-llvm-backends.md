# Chapter 12: The LLVM Backends and llvm_capi Parity

pcc's position on LLVM is written into the fourth of its seven obligations: LLVM is the oracle, not the owner. The second half of that obligation — how the self backend becomes a first-class execution root — belongs to Chapter 13. This chapter covers the first half: how pcc uses LLVM, and how, to avoid being locked into any one Python binding of LLVM, pcc rewrote an llvmlite-shaped IR builder and an LLVM-C binding inside the repository ([pcc/ir/](../../pcc/ir)), then used a parity-testing discipline to pin the old and new paths to the same semantics. The chapter answers three design questions that cannot be dodged: why llvmlite plays the oracle and llvm_capi plays the system under test; why text-level IR rewriting has been ratcheted down to a single `va_arg` exemption; and why the system-link path no longer hands IR text to the system compiler. Behind all three answers sits one principle: every piece of LLVM IR text may be parsed only by the LLVM that produced it.

## Chapter Overview: LLVM Has Two Roles Here

First separate two roles: LLVM can be a reliable reference, but it cannot remain pcc's owner forever. llvmlite serves as the oracle, the in-repository llvm_capi path is the system under test, and parity tests keep the two paths pinned to the same semantics.

- `--backend` chooses the execution route; the compat gate chooses which IR builder constructs IR. Do not collapse those axes.
- Parity testing is not "the output looks similar"; it pins IR shape, verification, runtime behavior, and the allowed exemptions.
- Textual IR should be parsed only by the LLVM that produced it; otherwise version skew masquerades as compiler failure.

## 12.1 The Problem and the Design Space: Why Write Your Own LLVM Binding

pcc started out standing on llvmlite. llvmlite is the LLVM Python binding maintained by the Numba project, and it exposes two API layers: `llvmlite.ir`, a pure-Python IR builder that produces IR text, and `llvmlite.binding`, a C extension that wraps parsing, verification, optimization, MCJIT, and target-machine emission. Both pcc's C code generation ([pcc/frontends/c/codegen/c_codegen.py](../../pcc/frontends/c/codegen/c_codegen.py)) and its Python frontend lowering were written against this API, and the repository pins `llvmlite==0.46.0` in [pyproject.toml](../../pyproject.toml).

The problem surfaces at self-hosting. llvmlite's binding layer is a CPython C extension: a bootstrap binary that wants to live without libpython cannot `import llvmlite` at runtime. The module comment in [pcc/ir/__init__.py](../../pcc/ir/__init__.py) states the consequence bluntly: the chosen bootstrap strategy "requires replacing llvmlite with a hand-written, pcc-compilable LLVM-C-API binding so the self-hosted binary has no Python-C-extension runtime dependency."

The design space had three options:

1. **Depend on llvmlite forever.** Rejected: it conflicts directly with the self-hosting fixed point (Chapter 15) and violates obligation 4 — LLVM stays the owner forever.
2. **Jump straight to the self backend.** Rejected: cutting LLVM loose before the self backend covers full instruction selection, ABI, and relocation means throwing away a mature optimizer and multi-target support in the same motion, with no reference to compare against during the transition.
3. **Build an llvmlite-shaped stand-in inside the repository**: an IR builder with the same class names and method signatures, plus a narrow binding over the LLVM-C API; old and new switchable, default behavior unchanged.

pcc took the third option — and measured before writing a line. [docs/plans/llvmcapi-beta4-backlog.md](../../docs/plans/llvmcapi-beta4-backlog.md) records the β4.0 phase (marked complete 2026-04-21), which traced API calls under real workloads: across the py_corpus, inline-C, and ir_passes tests plus one `-g` run, pcc's **external** use of llvmlite amounted to roughly 40 APIs — 34 `ir.*` builder call sites plus 5 hot `binding` APIs (`parse_assembly` and `verify` accounted for all binding calls). The trace also showed a "long tail" of roughly 310,000 calls, every one of which was llvmlite invoking its own internals while serializing during `str(module)` — calls a text-emitting replacement would never need to replicate. That measurement turned "rewrite llvmlite," which sounds like a bottomless pit, into an 800–1000-line tiered task in the backlog (Tier 1: twelve classes sufficient to compile; Tier 2: common instructions; Tier 3: exception handling; Tier 4: long-tail arithmetic sharing a single binop helper). Measure the used surface first, then decide the rewrite boundary — that is the most portable lesson in this chapter.

The engineering principles for the transition are written in [docs/plans/dual-llvm-backend-compat-plan.md](../../docs/plans/dual-llvm-backend-compat-plan.md): default behavior unchanged, every new feature gated behind an explicit flag, every new backend must have a "fall back to llvmlite" strategy, and each phase touches only a few modules. This is not conservatism as rhetoric — the parity-testing method of §12.5 only works because the old and new paths coexist long-term and can be switched at any moment.

## 12.2 Two Switching Axes: `--backend` and the Compat Gate

Before describing the mechanism, two switching axes that are routinely conflated must be separated; otherwise the mode labels in the rest of this chapter will be wrong.

**Axis one: backend kind.** `_BACKEND_TABLE` in [pcc/backend/__init__.py](../../pcc/backend/__init__.py) registers three backends — `llvm`, `llvm_capi`, and `self` — resolved by `resolve_backend()` from the `--backend` flag or the `PCC_BACKEND` environment variable. `llvm` is the public default; `self` is marked unsupported, and `resolve_backend()` raises `BackendUnavailable` unless it is selected explicitly (see Chapter 13). Each `BackendConfig`'s `cache_signature()` feeds the compilation cache key, so switching backends necessarily invalidates the cache. One fact deserves honest labeling: on the execution path in [pcc/frontends/c/evaluator/c_evaluator.py](../../pcc/frontends/c/evaluator/c_evaluator.py), only `self.backend == "self"` gets a dedicated branch; the `llvm` and `llvm_capi` values share the same evaluator code path. Today this axis mostly distinguishes self from non-self; `llvm_capi` as a backend kind is annotated in the table as a placeholder selection, affecting the cache signature rather than the execution path.

**Axis two: builder library.** What actually decides *which code constructs the IR* is [pcc/ir/compat.py](../../pcc/ir/compat.py). Codegen modules never import llvmlite directly; instead:

```python
from pcc.ir.compat import ir_c as ir      # C codegen
from pcc.ir.compat import ir_py as ir     # Python codegen
from pcc.ir.compat import ir_passes as ir # IR passes
```

At import time, compat reads a family of environment flags: `PCC_USE_LLVMLITE` falls the whole system back to llvmlite, while `PCC_USE_LLVMLITE_PY` / `PCC_USE_LLVMLITE_C` / `PCC_USE_LLVMLITE_PASSES` fall back per subsystem. **The default — no flags — is `pcc.ir`.** This is the "default flip" that has already happened: the earlier opt-in flags `PCC_USE_LLVMCAPI*` were retired as no-ops at flip time, and the flag semantics inverted from "dare to enable the new thing" to "do you need to retreat to the old one." The per-subsystem split exists for regression isolation: a regression in the Python frontend builder should not force rolling back the C frontend and the pass layer with it.

Zero call-site changes is the hard requirement of this layer. After the first line `from pcc.ir.compat import ir_c as ir` in [pcc/frontends/c/codegen/c_codegen.py](../../pcc/frontends/c/codegen/c_codegen.py), the entire file does not know which builder it is using. The one shape difference is absorbed by compat's `set_struct_body()` adapter: llvmlite's `IdentifiedStructType.set_body(*elements)` takes variadic positional arguments with no `packed` keyword, while the pcc side takes a single iterable plus `packed=`; the adapter dispatches on the class's `__module__` prefix.

One asymmetry must also be stated plainly: the top of [pcc/frontends/c/evaluator/c_evaluator.py](../../pcc/frontends/c/evaluator/c_evaluator.py) still reads `import llvmlite.binding as llvm` — the host evaluator's main path for parsing, verification, optimization, MCJIT, and object emission is carried by llvmlite's binding to this day. The current consumers of `pcc.ir.binding` are the in-memory pass-pipeline transport (§12.7), the Python frontend's `ir_pass_pipeline.py`, and the self-hosting closure; its competence across the full parse/verify/JIT/emit_object chain is proven by a separate gate, [tests/c/test_llvm_capi_end_to_end.py](../../tests/c/test_llvm_capi_end_to_end.py) (§12.5). "The builder default has flipped" and "the evaluator binding has been replaced" are two distinct claims, and this book makes only the first.

## 12.3 The Text-First Builder: [pcc/ir/ir.py](../../pcc/ir/ir.py)

The first sentence of [pcc/ir/ir.py](../../pcc/ir/ir.py) is a design position: a "text-first IR builder ... constructs LLVM IR incrementally as text (no object graph), with `str(module)` producing the complete IR string." llvmlite's `ir` layer maintains a genuine object graph and walks it at serialization time; pcc's stand-in renders each instruction into its final text line at the moment of the builder call.

Two independent reasons support this decision. The first comes from the β4.0 measurement: those 310,000 long-tail calls were llvmlite's internal machinery for serializing its own object graph, and direct text emission has no need for them to exist. The second is more fundamental: **this file has to be compiled by pcc itself.** The module comment states the implementation philosophy — "statically typed Python, no heavy reflection, ready for self-host compilation" — and the constraint leaves fingerprints everywhere. The comment on `ModuleRef.functions` explains why it returns a list rather than a generator ("the self-host audit flags `yield` as a blocker"); `Module.__str__` concatenates with a `while` loop and `_join_text` instead of a generator expression. The closure-mapping function in [pcc/frontends/python/pipeline.py](../../pcc/frontends/python/pipeline.py) tightens this line at the link layer: under `--ir-scaffold=on`, the source closure of a stage binary includes `pcc.ir.ir` (natively compiled in as `user_pcc_ir_ir_*` symbols) while **excluding** `compat.py` and `binding.py` — the comment says outright that keeping the LLVM-C/JIT binding in the closure "is the hand that drags libpython back into the self-backend path." The layering comes out clean: a self-hosted pcc1 constructs IR text with the ir.py compiled into itself, and the consumer of that text is the self backend (Chapter 13), not an in-process LLVM.

Text-first does not mean discarding structure. A `Block` holds a list of `InstructionRecord`s, each a triple of text line, opname, and owning block; `_opname_of()` extracts the operation name from the leading token of the text line, so codegen can still ask "is this an alloca / a terminator." A `Value` carries its type and reference form (`%tmp3`, `@glob`, or a constant literal) and keeps an `_instr` pointer back to the defining instruction record: llvmlite permits rewriting an instruction's fast-math flag list after the fact, and pcc honors the same mutable semantics by having `_refresh_flags()` rewrite the record's text. `IRBuilder` simulates llvmlite's insertion anchor with an integer insertion position `_pos`, and deliberately exposes an `_anchor` attribute alias — because some of pcc's own codegen helpers save and restore llvmlite's internal name `_anchor` directly. Compatibility carried to this depth says one thing: the target of parity is not the documented API but **everything callers have ever touched**.

Two semantic alignments with llvmlite deserve to be named individually, because both paid tuition in later regressions (§12.8):

- **Integer-type interning.** `IntType` is interned by bit width, so `IntType(64) is IntType(64)` holds — codegen is full of identity checks of the form `value.type is _I64`, and textual equality is not enough.
- **Pointee tracking under opaque pointers.** With LLVM 15+ every pointer's textual form is just `ptr`, but `PointerType` still stores its `pointee`, and `__eq__` compares address space and pointee; `_same_tracked_type()` recurses through pointees the same way. The lesson is written into the investigation record: do not "treat all opaque pointers as equal because the text is uniformly `ptr`" — GEP result types and load widths are derived entirely from the tracked pointee.

The builder also performs defensive elision: a same-type `sext`/`zext`/`trunc`/`fpext`/`fptrunc`/`bitcast` returns the original value without emitting an instruction (the regression test `test_pcc_ir_builder_elides_same_type_casts` pins this behavior). `Value` carries three pcc-private slots — `_is_unsigned`, `_pcc_unsigned_pointee`, `_pcc_unsigned_return`. Chapter 4 explained that signedness in the C lowering layer is metadata tracked separately from the IR type; these slots are where that metadata lands at the builder layer. The tail of the file holds a family of monomorphized wrappers — `FunctionType___init__2`, `IRBuilder_call4_i32`, `scaffold_Constant_i64`, and so on — flattening variadic constructors into fixed-arity entry points for the restricted typed frontend. Finally, byte-level textual identity with llvmlite (anonymous temporary numbering and the like) was explicitly excluded from the β4.1 scope and classified as β4.3 polish — semantic equivalence before byte equivalence, a ranking that reappears in the test design of §12.5.

## 12.4 `binding.py`: A Narrow Surface over ctypes

[pcc/ir/binding.py](../../pcc/ir/binding.py) describes itself as "a β4.2 drop-in for `llvmlite.binding`," implementing exactly the narrow surface the β4.0 trace delimited: `parse_assembly(text)`, `ModuleRef.verify()`, iteration over `ModuleRef.functions`, `Target.from_triple` / `from_default_triple` / `create_target_machine`, `create_mcjit_compiler`, `ExecutionEngine.get_function_address`, `TargetMachine.emit_object` / `emit_assembly`, target initialization, and the later additions `run_passes` / `run_passes_on_ir`. In host form it opens `libLLVM-C` through ctypes: `_find_libllvm()` tries, in order, the `PCC_LIBLLVM_PATH` environment variable, a table of Homebrew/Linux candidate paths, and `ctypes.util.find_library`. In self-hosted form the same set of function declarations is bound at AOT compile time via `pcc.extern` — [pcc/ir/__init__.py](../../pcc/ir/__init__.py) is that extern declaration manifest.

Several implementation details show the "narrow but correct" orientation:

- `_configure_bindings()` sets explicit `argtypes`/`restype` for every LLVM-C function used; the comment notes this guards against pointer truncation on 64-bit platforms. `LLVMInitializeNativeTarget` is a header macro, not an exported symbol, so the initialization routine probes both the x86 and AArch64 symbol families one by one with `_call_if_present`.
- Every `char*` returned by LLVM is copied via `_consume_msg()` and immediately released with `LLVMDisposeMessage`; `LLVMParseIRInContext` takes ownership of the memory buffer, which must not be freed again after the call; on success, `create_mcjit_compiler()` sets `mod._owns = False` — the execution engine takes ownership of the module. These ownership comments are the same discipline as the owned/borrowed reference contract of Chapter 9, with LLVM handles substituted for Python objects.
- `parse_assembly()` rewrites the builder's default placeholder triple `unknown-unknown-unknown` to the host triple — MCJIT reports "No available targets" for the placeholder, and llvmlite likewise applies the host triple when none is set, so behavior is aligned at exactly that level.
- `run_passes()` goes through `LLVMRunPasses`, the C interface to LLVM's new pass manager; the pipeline-string syntax is the same as `opt -passes=` (profiles like `default<O2>` are supported), and `mod.verify()` is forced after the run. This entry point is what carries the in-memory pipeline transport of §12.7.

## 12.5 The Parity Method: llvmlite as Oracle, llvm_capi as System Under Test

First mandatory question: why this direction of roles, and not the reverse? Three mutually independent reasons.

**First, historical asymmetry.** pcc's two codegens were written against llvmlite's API and behavior; the llvmlite path encodes the entire "established intent" — the return type, mutability, and naming behavior each call site expects. `pcc.ir` is the stand-in written later for self-hosting, and its very definition of correctness is "agrees with the established intent." Only the newcomer can be the system under test.

**Second, maturity asymmetry.** llvmlite has been hardened by years of production load across the Numba ecosystem; [pcc/ir/ir.py](../../pcc/ir/ir.py) is new single-repository code. Taking the battle-tested side as the frame of reference is the backend-layer instance of the Chapter 3 debugging principle, "compare against a known-good reference" — AGENTS.md lists it as one of the repository's three debugging pillars: native compilers for C, CPython for Python, llvmlite for `llvm_capi`.

**Third, a controlled variable.** The compat gate (§12.2) lets the same codegen, the same source file, and the same test switch between the two builders on nothing but an environment variable. When a difference appears, the only variable is the builder itself — a controlled experiment, not a loose comparison between two systems.

But the oracle's boundary must be stated: llvmlite is the **frame of reference**, not the source of truth. The final arbiter is LLVM itself — both sides' output must pass LLVM's parser and verifier, and execution parity is adjudicated by the numbers MCJIT actually computes. Wherever llvmlite is wrong (it is, after all, only a binding), the LLVM verifier and the runtime result will overrule both sides at once.

[tests/c/test_llvm_capi_ir_parity.py](../../tests/c/test_llvm_capi_ir_parity.py) encodes this thinking as a three-level gate. Each test feeds the same `_build(ir_mod)` function into both `llvmlite.ir` and `pcc.ir.ir`:

1. **Parseable and verifiable.** Both sides' `str(module)` must pass `llvm.parse_assembly` plus `verify()`; when the system under test fails, the full IR source text is included in the assertion message.
2. **Identical structural signature.** `_structural_signature()` extracts, from the **parsed** ModuleRef, a tuple of function names, signature text, per-block instruction counts, per-block terminator opcodes, and global variable names and types, and compares them. The signature deliberately skips anonymous temporary numbering — a harmless divergence between the two builders, explicitly filed under β4.3 textual polish rather than the Level-1 hard gate. Comparing on the parsed module means comparing the structure as LLVM sees it, not as strings.
3. **Execution parity.** The strongest level: `_jit_call_int_int()` hands each side's module to MCJIT, calls the function, and compares return values — `test_execution_parity_recursive` requires both sides to compute 55 from a recursive fib. The test file's comment says it plainly: only when LLVM JITs both modules into machine code that behaves identically is semantic equivalence proven.

[tests/c/test_llvm_capi_end_to_end.py](../../tests/c/test_llvm_capi_end_to_end.py) supplies the other half of the loop: it never imports llvmlite at all. IR is constructed by `pcc_ir`, parsed by `pcc_bind.parse_assembly`, verified, executed under MCJIT (recursive fib, a loop sum with phi), emitted as an object via `TargetMachine.emit_object` with the Mach-O/ELF/COFF magic checked — plus one negative test: bad IR must be rejected (`test_verify_rejects_bad_ir`). The parity tests prove "the new builder is equivalent to the old builder"; the end-to-end tests prove "the new builder plus the new binding closes its own loop." Both kinds of evidence are necessary, because the former depends on llvmlite being present, and self-hosting is precisely the scenario where llvmlite leaves the stage.

The pass layer has an isomorphic parity check: [tests/c/test_llvm_capi_pass_pipeline.py](../../tests/c/test_llvm_capi_pass_pipeline.py) uses `run_passes_on_ir("mem2reg,instcombine")` to verify that stack-slot promotion really happens (`alloca`/`store`/`load` vanish, `ret i32 42` appears), then compares the in-memory pipeline output against the external `opt` text-pipeline output word for word after both pass through `normalize_ir()` in [pcc/ir_passes/parity.py](../../pcc/ir_passes/parity.py) (strip ModuleID and `attributes #N`, densely renumber anonymous SSA names per function, collapse blank lines).

The last piece of the method is its boundary of applicability, stressed both by [docs/debugging-playbook.md](../../docs/debugging-playbook.md) §3 and by the investigation record in §12.8: llvmlite is the oracle for missing builder instructions, constant GEP/bitcast, opaque-pointer type semantics, and function-pointer decay. It is **not** the oracle for preprocessor behavior, fake-libc header policy, parser acceptance, or compile-time diagnostics — if both builders fail the same way, the bug lives above the builder layer, and forcing the failure into a backend-parity story only wastes the evidence chain.

## 12.6 The IR Fix Policy: A Ratchet on Text Rewriting

The IR Fix Policy section of AGENTS.md is the standing constitution of this rule: semantic bugs belong in parser/codegen source logic; `postprocess_ir_text()` is acceptable only for narrow lowering gaps the IR builder cannot directly express; **the only acceptable text-level lowering remaining today is the `va_arg` path** — any other text fix is a compiler source bug to be fixed before serialization; and CFG, type, or signedness bugs must never be hidden behind text rewrites.

This is the endpoint of a tightening ratchet, not fastidiousness present from day one. The AGENTS.md of 2026-03-23 in git history (commit `bc1f1018`) records the full roster of `postprocess_ir_text` fixes then on the books: rewriting integer-to-pointer `bitcast` into `inttoptr`; rewriting Python `<ir.Constant>` reprs that leaked into the IR as `zeroinitializer`; deleting void `alloca/load/store`; deduplicating repeated switch cases; deleting dead code after terminators; patching consecutive empty labels with `br`/`unreachable`. Six fix classes, each a textual bandage over a codegen source bug — a repr leak means constant lowering `str()`ed a Python object straight into the IR on some path; empty labels mean CFG construction dropped a terminator somewhere. The policy of that era could only demand "keep text fixes centralized in one place, don't scatter them into test helpers" (and that document already saw through it: a fix that exists only in test code does nothing for `uv run pcc`). Subsequent work converted the six bandages into source-level fixes one by one, and the ratchet tightened into today's form.

Today's `postprocess_ir_text()` ([pcc/frontends/c/codegen/c_codegen.py](../../pcc/frontends/c/codegen/c_codegen.py)) is a one-line delegation; the real implementation moved into `postprocess_varargs_ir()` in [pcc/frontends/c/codegen/c_varargs.py](../../pcc/frontends/c/codegen/c_varargs.py). The justification for the exemption is builder expressiveness, not semantics: within the subset pcc uses, llvmlite's IR layer cannot directly emit LLVM's `va_arg` instruction, so the C codegen first emits an ordinary placeholder call to a `__pcc_va_arg_N` helper, and at text time two regular expressions complete the lowering — `_PCC_VAARG_DECL_RE` deletes the helper declarations, `_PCC_VAARG_CALL_RE` rewrites the calls into real `va_arg` instructions. This is precisely the policy's defined "narrow gap the builder cannot express": the rewrite changes no semantics already expressed; it only supplies an instruction the builder cannot emit.

And the exemption is audited, not merely tolerated: `postprocess_ir_text_with_report()` returns a structured `VarargsRewriteReport` (schema string `pcc.c.varargs_rewrite.v1`, recording per rewrite the helper name, lvalue, argument types and values, and result type). A text rewrite that has to stay must at minimum be countable, serializable, and visible to tooling.

Why be this severe about text rewriting? Because regular expressions cannot see the CFG or the type system. A rule that mutates text before verification moves a codegen bug to the least attributable position in the entire pipeline: IR text is codegen's output and LLVM's input, so patching there contaminates the evidence on both sides at once. The Chapter 4 signedness lesson — bits correct, signedness metadata lost — recurs at the text layer in a more insidious form: a text rewrite simply cannot see that "this value is supposed to be unsigned."

## 12.7 The System-Link Path: Optimize in Memory, Emit Objects Directly

`--system-link` mode — compile multiple translation units, then let the system toolchain link them into a real executable — is the historical hot zone for version-skew problems. The current implementation ([pcc/frontends/c/evaluator/c_evaluator.py](../../pcc/frontends/c/evaluator/c_evaluator.py)) runs this chain:

```text
.c files ──compile_translation_units()──► list of (unit_name, ir_text, ...)
                                              │  per unit
                                              ▼
                          _prepare_llvm_module(unit_name, ir_text, tm)
                            ├─ repository-managed LLVM optimization (one of three routes, below)
                            └─ llvm.parse_assembly + optional PCC_DUMP_BAD_IR dump
                                              │
                                              ▼
                          target_machine.emit_object(llvmmod) ──► .o file
                                              │
                                              ▼
                      system cc: link the .o files only (+ platform flags; -no-pie on Linux)
```

`run_translation_units_with_system_cc()` first runs the frontend to get each TU's IR text; then `run_compiled_translation_units_with_system_cc()` calls `_prepare_llvm_module()` per unit to parse and optimize, emits native object bytes directly via `target_machine.emit_object()` into `.o` files, and finally assembles a `cc` command containing nothing but object files to link. **The system compiler never sees a single byte of LLVM IR text** — it does only the one thing it is least version-sensitive about: linking.

Which LLVM the optimization happens inside has three controlled routes, all repository-managed:

- Default: `_apply_llvm_optimizations()` optimizes the parsed module in-process within llvmlite, via `PassPipeline.run_backend_tier`.
- `PCC_LLVM_PIPELINE`, an explicit text pipeline: [pcc/frontends/c/passes/llvm_text_pipeline.py](../../pcc/frontends/c/passes/llvm_text_pipeline.py) uses `opt --print-pipeline-passes` to expand profiles like `default<O2>`, prunes disabled passes, and executes via `opt -S -passes=...`. The crux is `find_opt_binary()`: a candidate `opt`'s version must be **equal** to llvmlite's LLVM version, or the function returns None rather than use it.
- `PCC_LLVM_PIPELINE_TRANSPORT=memory`: the same pipeline string runs in memory through `pcc.ir.binding.run_passes_on_ir()` (`LLVMRunPasses`), eliminating the subprocess and the two text round-trips.

Here the third mandatory question gets its full answer: system-link no longer hands IR text to the system compiler because that handoff was the only scenario in which "two different versions of LLVM parse the same IR text," and the incident in §12.8 proved that scenario structurally unreliable. The standing invariant of the current design: IR text flows only inside the LLVM that produced it — llvmlite itself, a version-checked same-version `opt`, or `LLVMRunPasses` on the same libLLVM — and only native objects cross toolchain boundaries. AGENTS.md keeps one defensive clause for the future: should a text-IR handoff ever be reintroduced, attribute stripping (`nuw`, `nneg`, `range()`, `initializes()`, `dead_on_unwind`) must be centralized in `postprocess_ir_text()`. That clause is institutional memory of an incident, not a description of the present: today's code contains no attribute-stripping logic at all, because no handoff needs it.

## 12.8 History and Lessons

### 12.8.1 LLVM Version Skew and the Five Attributes (2026-03-23)

**Symptom.** When pcc wrote IR text to a file and compiled it with `cc -c`, any IR that had been through O2 optimization was rejected by the system clang's parser; the same IR ran fine on the JIT path.

**Root cause.** llvmlite bundles its own LLVM, usually newer than the system clang. The newer optimizer emits attributes in its output that the older parser does not recognize: `nuw` (in its newer use on getelementptr), `nneg`, `range()`, `initializes()`, `dead_on_unwind`. There is nothing mysterious about the JIT path's immunity — llvmlite parses its own output, so the versions are identical by construction; only the handoff of "text written out, read back by a different LLVM" explodes.

**The equilibrium of the time, and its costs.** The 2026-03-23 AGENTS.md (commit `bc1f1018`) records the engineering compromise then in force: the test compilation path simply **skipped** LLVM optimization to dodge the attribute problem, and the documentation advised that "if you must compile optimized IR with the system compiler, strip these attributes with regex post-processing." Both options run at a loss: the first costs system-link artifacts their O2; the second chases an attribute set that drifts with every LLVM release — the regex is forever one version behind.

**The real fix, and the invariant it left.** Eliminate the handoff itself: `run_translation_units_with_system_cc()` was rewritten as "repository LLVM optimizes in memory → `emit_object()` emits native objects directly → system cc only links," and the explicit text pipeline's `find_opt_binary()` made version equality a hard condition. The invariant was thereby established: **LLVM IR text does not cross LLVM version boundaries.** The sentence in today's IR Fix Policy — "if a text-IR handoff is reintroduced, centralize attribute stripping in `postprocess_ir_text()`" — is this incident's epitaph: it exists so that anyone repeating the mistake will at least concentrate the damage in one place.

### 12.8.2 How the Oracle Debugging Method Took Shape (2026-04-18)

**Background.** After the builder default flipped to `pcc.ir`, regressions began arriving in a new form: the same C source would fail to compile, or misbehave at runtime, under the default builder — and nobody could immediately say whether it was a semantic bug in codegen or a parity gap in the stand-in builder. [docs/investigations/llvm-capi-vs-llvmlite-oracle-debugging.md](../../docs/investigations/llvm-capi-vs-llvmlite-oracle-debugging.md) (filed 2026-04-18) records the standard procedure distilled from that batch of regressions.

**The method.** Five steps: minimize the reproducer → run once in the default environment → run the same reproducer again with `PCC_USE_LLVMLITE_C=1` → triage on three outcomes (fails only under `llvm_capi` = parity gap; both fail = the bug is above the builder layer; both compile but run differently = switch to dumping the frontend's unoptimized IR and take a minimal structural diff) → fix only the smallest semantic gap, add one focused regression, and run one realistic confirmation. The investigation deliberately includes a code template for the IR dump: feed the same source through `_compile_translation_unit_artifact_job` to extract `ir_text`, run it under both environments, and diff the minimal structural difference.

**Gaps actually fixed** (each one a product of this procedure, and each now pinned by a regression test): the builder lacked the four instruction methods `uitofp`/`fptoui`/`fpext`/`fneg`; constant-expression forms of `Value.gep()` / `Value.bitcast()` did not work (constant GEPs in global initializers came out as `null` or `0`); an `int ()` parameter must decay to a function pointer per C semantics, not to a fixed zero-argument function type; and the case already named in §12.3 — never treat all opaque pointer types as equal merely because the text is uniformly `ptr`.

**Lessons.** Two. First, controlled comparison before conjecture: in a subsystem with a built-in oracle, every "I think it's X" should first be cheaply confirmed or refuted by one rerun under `PCC_USE_LLVMLITE_C=1` — this is exactly the payoff of the compat gate's per-subsystem flags. Second, the oracle has a boundary: the investigation devotes a full section to what llvmlite is **not** the answer for (system preprocessor, header shim policy, compile-time diagnostics, parser acceptance), with the criterion "both sides fail → the bug is upstream." Forcing every failure into a backend-parity narrative wastes evidence just as surely as never running the comparison at all.

## 12.9 Summary

The LLVM side of pcc's story runs on one principle: **IR text is parsed only by the LLVM that produced it.** Three mechanisms follow from it: an llvmlite-shaped, text-first, pcc-self-compilable stand-in builder [pcc/ir/ir.py](../../pcc/ir/ir.py) plus the narrow binding `binding.py` (built for no-libpython self-hosting, Chapters 13 and 15); a three-level parity gate with llvmlite as the frame of reference and LLVM's parser/verifier/MCJIT as the arbiter, paired with an end-to-end closed-loop gate; and the "optimize in memory, emit objects directly" system-link chain. The policy surface converges on the same honesty: text-level IR rewriting has shrunk to a single, structured-report-bearing `va_arg` exemption; the compat gate provides controlled per-subsystem fallback; and claims stay mode-labeled — the builder default is now `pcc.ir`, while the host evaluator's main binding path is still llvmlite, and the two must not be conflated. Methodologically, this chapter offers three portable artifacts: trace the real API surface before rewriting; give every stand-in a one-switch oracle; and turn any dirty exemption you cannot remove into an auditable structured report.
